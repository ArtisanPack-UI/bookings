# ArtisanPack UI Bookings Changelog

## [Unreleased]

### Changed

- **The provider iCal feed is addressed by a token rather than by the provider's slug**: `GET bookings/ical/providers/{token}.ics`. The slug is published by `GET api/bookings/services/{slug}/providers`, so the route it replaces was a provider's whole diary behind a URL anybody who could read the booking widget could construct. Nothing is released yet, so the slug route is gone rather than deprecated.
- With the address unguessable, a provider feed carries the customer's name and email — which is what a provider looking at their week actually needs. `public.ical.provider_feed_details`, which existed only to keep them out of a feed anybody could reach, is removed.
- `service_providers.ical_token_hash` (`char(64)`, nullable, unique) holds `sha256(token)` and nothing else, the way `bookings.manage_token_hash` does. A leaked backup or a read-only replica hands over something that cannot be turned back into a working subscription. **The cost is that a lost URL cannot be recovered, only replaced.** The URL is not single-use — it goes into as many of a provider's calendar clients as they own — but nobody can read it off a screen twice, so rotation is the answer to a URL that has been lost or exposed, and it stops every calendar subscribed to the old one, silently, because a subscribed feed that starts 404ing does not announce itself. Weighed against a plain column that makes every copy of the database a working subscription to somebody's diary, and the hash won.
- Nothing mints a token on create. A provider has no feed until somebody asks for one, and a null hash is a 404 — which is both the safe default and the only coherent one, since minting at create time would throw the plain token away unread and leave a credential nobody could ever use.
- `Services\Concerns\MintsOpaqueTokens` now carries the primitives both credential schemes share — 32 CSPRNG bytes as 64 hex characters, `sha256`, `hash_equals()` — and `ManageTokenService` uses it too. Two independent implementations of the same primitive is the shape that ends with one of them quietly getting a weaker hash, or a `===` where the other has a constant-time compare, in a class nobody rereads because the other one is fine.
- The `ical_token` rate-limit bucket joins `ical`, keyed on the token rather than the address, so the provider feed is bounded per address *and* per URL exactly as the customer feed already was. A feed URL leaks the way a manage link does and then some: it is pasted into a calendar client and sits in its settings for years, syncing to whatever else that account is signed into.
- `bookings.rate-limit` reports the tightest allowance a request passed through rather than whichever bucket happened to run outermost. The manage read carries two of them, and each was overwriting the last one's `X-RateLimit-*` headers on the way out — so a widget could be told it had fifty-nine reads left by the per-token bucket while the per-address one had three, and pace itself into a 429 it had just been promised room for.
- `BookingService::complete()` claims the transition against the row rather than asserting it from the model in hand. The status check reads memory, and a plain `save()` writes by primary key with no condition — so a caller holding a booking that was cancelled underneath it overwrote the cancellation and then announced the completion, telling the customer their appointment was cancelled and their CRM that it was delivered. `bookings:complete-past` makes that the normal case rather than a rare one, since it walks a page at a time and a customer can cancel between the read and the write. The conditional update follows the idiom `Webhook::disable()` already uses: the database decides, the loser gets `InvalidBookingTransitionException`, and the hook and event fire only for whoever actually moved the row. Callers that already treat that exception as a normal outcome — the sweep does — need no change.

### Added

- `bookings:ical-token {provider} [--revoke] [--force]` issues, rotates, and withdraws a provider's feed token, and prints the subscription URL. Since only the hash is stored there is no screen anywhere that can show that URL a second time, so this command is the moment it exists in readable form — which is also why it warns and asks before replacing a token that is already in use. It takes an id or a slug, and reaches deactivated providers, because revoking the feed of somebody who has just left is exactly the thing an operator needs to do.
- `ap.bookings.icalTokenIssued` and `ap.bookings.icalTokenRevoked`. The first carries a live secret — the plain feed token, at the only moment it is readable — so an application with mail wired up can deliver the subscription URL itself. It fires on a rotation as well as a first issue, and by then the previous token is already dead, so a subscriber that sends the new URL is not being helpful: it is the only thing between the provider and a feed that has silently stopped updating.
- The subscribable calendars from plan §5.2: `GET bookings/ical/providers/{token}.ics` and `GET bookings/ical/customers/{token}.ics`, served by `Services\IcalFeedService` through `sabre/vobject`. A provider who wants their diary in Apple Calendar should not have to connect an account for it, and a customer adding one appointment to their phone should not have to either.
- These mount under `public.route_prefix` without the `api/` the JSON endpoints carry, because nothing calls them from a widget — a person pastes the address into a subscription box, and it is then fetched by software that guesses how to treat the URL from its extension, which is why the `.ics` is in the path rather than in a query string or a content negotiation.
- **Every request answers from an aggregate before it reads a booking.** A subscribed feed is refetched on a timer nobody here controls — Google roughly hourly, Apple about every fifteen minutes, forever, once per subscriber — so the entity tag is one `max` and two counts over an indexed range, and a matching `If-None-Match` ends the request with an empty `304` having built no models and serialised nothing. `Cache-Control: private, max-age=300` goes out with the 304 as well as with the body: a 304 that omitted it leaves the client holding a copy it may not reuse, and the next poll is a full fetch of a feed nothing changed in.
- The counts are in the tag alongside the newest `updated_at` because timestamps only detect changes that raise them. Cancelling the most recently touched booking in a window *lowers* the maximum, so a tag built from the timestamp alone — which is what §5.2 specifies — would have read exactly as it did before the cancellation, and every subscriber would have gone on showing an appointment that is not happening until something unrelated moved the tag. The total covers rows arriving and leaving; the published count covers a booking that stays in the table and stops being served. Soft-deleted and cancelled rows are counted for the same reason: their absence from the feed is the change a subscriber is waiting for.
- `If-None-Match` is parsed as the list it is, and a weak tag matches. A client that sends two tags, or a proxy that weakened the one it stored, would otherwise be told the feed had changed on every single poll — which is the entire cost these endpoints exist to avoid.
- The customer feed is guarded by the same `bookings.manage-token` middleware as the manage endpoints and carries the one booking that token stands for — not the customer's other appointments, and not the rest of a series — so a token discloses no more through its calendar than through the link it arrived in. It is limited per address *and* per token, because a feed URL escapes the way a manage link does: by sitting in a calendar client's settings for years.
- `UID` is built from `booking_number`, which is unique across the installation and never changes, so a reschedule moves the event a subscriber already has instead of leaving the old time behind next to a new one. `DTSTAMP` and `LAST-MODIFIED` are the booking's `updated_at` rather than the current time, which keeps two serialisations of an unchanged feed byte-identical — a `DTSTAMP` of "now" would hand a revalidating client a different document under the same entity tag.
- `public.ical.past_days` (30) and `future_days` (365) bound what one feed carries, measured from now so the window slides with the clock. An unbounded feed is the whole archive, serialised, on that refetch timer, once per subscriber; a calendar client has no use for last year's appointments. Zero or less on either side reads as "not configured" and falls back to the shipped window, as everywhere else in the config.
- The self-serve manage surface from plan §6.1: `GET api/bookings/manage/{token}`, `POST api/bookings/manage/{token}/cancel`, and `POST api/bookings/manage/{token}/reschedule`. A customer who booked without an account still has to be able to see, cancel, and move their appointment, and the token in the confirmation email is the only credential they have.
- `bookings.manage-token` middleware, which is the whole authentication layer for those three routes. It checks the token's shape before it goes near the database — 64 hex characters and nothing else can be one, so a scanner walking the path costs a regular expression rather than an indexed lookup — then resolves it through `ManageTokenService::findBooking()`, where the lookup is by hash and the decision is `hash_equals()`. Every failure gives the same 404 with the same message: an unknown token, a malformed one, and a token belonging to another site are indistinguishable from outside, because a 401 or a more specific message would confirm which guesses were closer.
- Both writes go through `BookingService`, so `ap.bookings.cancelling` / `cancelled` / `rescheduling` / `rescheduled` fire exactly once with `actor: customer` intact. The notifications, the webhooks, and the calendar sync all hang off those events and none of them can tell a customer cancelling from staff cancelling on the customer except by the actor — which is why nothing here touches the model directly.
- The reschedule endpoint re-resolves availability rather than trusting the time it was sent. The slot list a widget draws from was computed when the page loaded, and a manage link is often opened days later. That check is a courtesy rather than the guard: nothing holds a lock between resolving and writing, so the slot lock and the unique index inside `BookingService::reschedule()` still settle the race, and a 409 from there is the honest answer when two customers want the same freed slot. Its `start_time` is held to `booking_window` for the reason creation is — a slot last Tuesday is extremely free.
- `cancellation.min_advance_minutes` is now enforced, on rescheduling as well as cancelling. Moving an appointment an hour before it starts disrupts the diary exactly as much as cancelling it, and leaving reschedule ungated would have made it the way around the cancellation window. The read reports the policy as `meta.can_cancel`, `meta.can_reschedule`, and `meta.changes_allowed_until`, so a widget renders from the same answer the writes enforce instead of reimplementing it — the failure otherwise is a button that is drawn and then refused.
- A manage link keeps reading and cancelling after its service is switched off, and stops taking new time. Rescheduling into a withdrawn service would resolve availability from rules nobody is maintaining; cancelling one is exactly what a customer should still be able to do.
- The `manage_token` rate-limit bucket keys on the token rather than the address, so reads are bounded per-IP *and* per-link — one machine grinding through guesses and one leaked link being fetched from everywhere are different abuses and need different buckets. The limiters are declared before the resolver on every manage route, because middleware runs in declaration order and the other way round each guess would cost a database lookup before anything counted the guesses. The `TrustedProxies` documentation stays with #29.
- The public API from plan §6.1, mounted under `api/` plus `public.route_prefix`: `GET api/bookings/services`, `GET api/bookings/services/{slug}/providers`, `GET api/bookings/services/{slug}/slots?date=YYYY-MM&provider_id=`, and `POST api/bookings`. This is the contract the Livewire, React, and Vue widgets are written against, so the response shapes are deliberately narrower than the rows behind them — `metadata`, `site_id`, and `default_provider_id` are not a customer's business, and a provider's `email` and `phone` on an unauthenticated endpoint is a staff directory anybody can scrape.
- **The manage token is never returned.** Only its hash is stored and the plain value exists once, in the confirmation email (§9.2); an endpoint that echoed it would turn a one-copy credential into a two-copy one over an unauthenticated response.
- Every string a customer sends goes through `artisanpack-ui/security` before the rules run rather than after, so what validation passes judgement on is what will actually be stored — a name whose markup strips to nothing fails `required` instead of being written as an empty string. Intake answers are cleaned recursively, because the security package's own `sanitizeArray()` maps over one level and hands each value to a string sanitizer, which a checkbox group walks straight into.
- The attributes handed to `BookingService` are rebuilt field by field rather than passed through. That service accepts `series_id`, `series_index`, and a caller-named assignment strategy, none of which an anonymous request over the internet has any business setting.
- A submission carrying more than a hundred answers is refused, counted at every depth rather than at the top level — one key holding a hundred thousand children satisfies a `max` rule — and counted *before* it is sanitized, so the cost of refusing a hostile body is bounded by the cap rather than by the body.
- Both the slots query and the booking write are held to `booking_window`. Nothing further down enforces it: availability is computed from schedules and existing bookings and knows nothing about the current time, so a slot last Tuesday is extremely free, and without this the endpoint would have offered this morning at four in the afternoon and taken bookings for it.
- `bookings.rate-limit` middleware, guarding `POST api/bookings` at `public.rate_limits.post` (five a minute by default). Buckets are named rather than numeric so limits live in configuration an installation can raise, and a bucket name the middleware does not know throws rather than silently guarding nothing. **The buckets key on the client IP, so they are only as truthful as `TrustedProxies` is configured to make them** — the per-token buckets and the README section on this are #29.
- A slug that names no bookable service answers with a plain 404 rather than `firstOrFail()`'s, whose message names the model class — a detail of this package's internals otherwise handed to anybody who mistypes a slug.
- `bookings:prune-webhook-deliveries` reports pending deliveries that have outlived the retention window instead of passing over them in silence. Exempting them from the delete is deliberate, but a `payload` holds the customer's name, their email, and their appointment, so a stuck delivery keeps that data indefinitely for exactly the rows nobody is watching — the retention window quietly not applying. The whole argument for keeping the row is that somebody should go and look at it, which only works if something says so.
- The scheduled commands from plan §5.7, registered on the application's schedule by the service provider: `bookings:send-reminders` every fifteen minutes, `bookings:complete-past` hourly, `bookings:calendar-refresh` daily, `bookings:calendar-watch-renew` hourly, `bookings:calendar-apple-poll` every fifteen minutes, and the three prunes overnight. `bookings:reissue-detached-manage-tokens` is deliberately not among them: it invalidates every manage link the package has ever sent, which is something an operator does in response to a leak and nothing a clock should decide to do.
- `bookings:complete-past` closes out confirmed bookings whose end time has passed. It goes through `BookingService::complete()` rather than updating the status column, which is what makes `ap.bookings.completed` fire exactly once per booking and the `BookingCompleted` event go out with it — a bare update would move the same rows and tell nobody, so the follow-up email, the review request, and the invoice hanging off that event would never happen. Only `confirmed` bookings are swept: a `requested` one is an appointment nobody approved, and marking it delivered would be the package asserting that something happened which may never have been accepted.
- `--dry-run` on everything destructive, and on `bookings:complete-past` that means genuinely inert — the candidate query is counted rather than walked and the service is never touched, so no hook fires and no event dispatches. A dry run a subscriber can email a customer during is not a dry run.
- `bookings:prune-notification-log`, `bookings:prune-webhook-deliveries`, and `bookings:prune-calendar-events`, reading their windows from `retention`. A window of zero or less is read as "not configured" and prunes nothing rather than as "keep nothing": a blank environment variable is a likelier way to reach zero than a retention policy is, and the notification log is the thing that stops a reminder being sent twice — an installation that shortens its window below its longest reminder is asking for a customer to be emailed twice.
- A `pending` webhook delivery is never pruned however old it is. The backoff schedule spans about fourteen hours against a default retention of thirty days, so a pending row that old is one nothing has picked up — but deleting it makes the delivery stop existing rather than fail, and the endpoint that should have received the event never hears about it with nothing anywhere to say why. A stuck delivery is a queue to look at, not a row to tidy away.
- Calendar mappings are pruned by the booking's end time rather than by the row's own age, because a mapping for a booking a year out is older than one for yesterday's appointment and matters far more — pruning by `created_at` would delete exactly the rows a reschedule still needs to follow. Deleting the row does not delete the external event, and is not meant to: that event is on a calendar this package does not own, describing an appointment that genuinely happened.
- `retention.webhook_delivery_days` joins the retention block, falling back to `webhooks.delivery_retention_days` when unset so an installation that configured either gets the window it asked for. **Only an absent setting defers**, because a zero and a typo both read as "not configured" and deferring on those would turn switching the prune off into pruning at somebody else's thirty days — destructively, and against what the config comment promises.
- Every comparison against `end_time` is made in UTC explicitly. The column is written as UTC and a bound `Carbon` is rendered by `format()` in its own zone with no conversion, so an application whose `app.timezone` is Asia/Tokyo would have had `bookings:complete-past` mark appointments finished nine hours before they were — firing `BookingCompleted`, and with it the follow-up email and the invoice, while the customer was still in the room. `retention` cutoffs stay in the application's zone, which is what `created_at` is stored in; the two conventions genuinely differ and only diverge off UTC.
- `bookings:complete-past` eager loads the service and provider across every site. The webhook body names both, and the listener's own `loadMissing()` runs through the site scope — so on an installation whose resolver answers in console, every tenant but the resolved one would have had `service: null, provider: null` posted to their integration, silently, because the payload builder null-guards.
- `bookings:calendar-watch-renew` ignores channels on disabled connections. `CalendarConnection::disable()` clears the sync token and leaves the watch rows behind, so a connection disabled for a revoked token would have reported its channels as due every hour forever — and the whole design of these sweeps rests on that warning still being worth reading.
- Every scheduled command's overlap lock is given an expiry sized to its cadence rather than the framework's twenty-four hour default. The lock is released when a run finishes, so the expiry only matters when one never does — a SIGKILL, an OOM kill, a container replaced mid-sweep — and a day-long default means one of those silences the command until tomorrow. For the Apple poll that is exactly the failure polling exists to prevent, since CalDAV has no push to fall back on.
- The prunes delete by a page of primary keys rather than in one statement. A first prune on an installation that has never run one can match years of rows, and a single delete that wide holds locks for as long as it takes.
- `bookings:calendar-refresh`, `bookings:calendar-watch-renew`, and `bookings:calendar-apple-poll` sweep for the work that is due — two-way connections, push registrations lapsing within the hour or already lapsed, two-way Apple connections — and report it. Acting on it needs a `CalendarSyncDriver`, and those ship in `artisanpack-ui/google`, `artisanpack-ui/microsoft`, and `artisanpack-ui/apple`, none of which this package depends on; until one is installed the sweeps warn rather than exit silently, because a calendar that has stopped being read still shows availability and the failure is otherwise invisible from the outside. Each is scheduled only when its driver is switched on, so an installation that has never connected a calendar has nothing waking up to say so.
- Every scheduled command is registered `withoutOverlapping()`. None of them needs it for correctness — the reminder sweep claims each send in the notification log, the completion sweep re-reads the status it transitions, and a prune deleting rows another prune already deleted is a no-op — but a doubled run is a lot of database round trips to do nothing.
- The completion sweep reads across every site, for the reason the reminder sweep does: it runs from cron where nothing has resolved a site, and an application whose resolver answers in console too would otherwise close out one tenant's bookings and leave every other tenant's confirmed forever.
- `Contracts\SmsDriver` and `Notifications\Sms\NullSmsDriver` per plan §5.1, with an `sms` notification channel wired to them. The contract is one method taking a number and a string, which is the point of splitting it from `NotificationChannel`: the channel is the half that knows about bookings — whether there is a number, what the message says, what the log records — and the driver is the half that knows about a gateway, so a Twilio or Vonage integration is one class with one method and never sees an appointment. Those two land in v1.1; this is the contract they will satisfy.
- The shipped driver logs at info level and sends nothing. Info rather than debug because a message that was meant to go out and did not is worth seeing in a default log configuration, and production — where somebody is asking why the customer never got their text — is exactly where debug is off. The number is logged in full: it is already in `bookings.customer_phone` and in the notification log's `recipient`, so redacting it here would hide it from the one place trying to explain a delivery while leaving it everywhere else, and confirming the right number *would* have been texted is the whole use of this driver.
- `notifications.sms_driver` takes `null` — the default — or the name of a class implementing the contract, so an application points the setting at its own gateway from `.env` without touching the container. A name rather than a key out of a driver map, because the package ships one driver and a map of one entry is a list of the gateways an application is not allowed to use. A name that does not resolve throws rather than falling back to the null driver: an installation that configured Twilio and is quietly writing log lines has every customer unreachable and nothing looking wrong, which is how a typo in a class name goes unnoticed for a month.
- **`sms` is not in the default channel list, and installing a driver does not add it.** Texts cost money per message and arrive on a real phone, so the channel is registered rather than enabled — listing it in `notifications.channels`, or adding it from `ap.bookings.notification.channels`, is what makes it send. That filter is how an installation texts cancellations but not confirmations, or only customers who asked to be texted, and how a gateway shipped out of tree opts itself in. The ticket consumes the hook rather than hardcoding a channel, so nothing in core changes when a real driver arrives.
- The driver is resolved when a text is sent rather than when the channel is built, and `SmsChannel` is constructed explicitly rather than autowired so the container does not helpfully fill the argument in at boot. A misconfigured gateway therefore costs one notification — recorded against the log as failed, logged, the other channels unaffected — instead of costing the application its boot.
- Two things about SMS are documented rather than solved, because solving them in a package would mean guessing. The null driver's log line holds a customer's number and the time of their appointment, in a file the erasure routine does not sweep — it walks `bookings` and `booking_notification_log`, and nothing walks `storage/logs` — so it is a development aid rather than a way to run with `sms` enabled and no gateway. And a phone number on a booking is attacker-supplied wherever the widget is public, which makes a bound gateway a way to have somebody else's application text a number at your expense; rate limits, texting on confirmation rather than on request, and a region check belong to whoever knows which numbers are legitimate.
- `BookingNotification::toSms()` renders the email's opening line and appointment details without the greeting, from the same two methods the mail body uses rather than as a second copy of the wording, so a correction to a lifecycle message reaches both. It takes no notifiable, unlike `toMail()` and `toArray()`: there is none to take, the customer has no account, and a parameter that could only ever be null is one a subscriber's own `toSms()` would have to declare and ignore. The channel asks for the method by name, because a subscriber to `ap.bookings.notification.sending` may have replaced the notification with anything, and refuses one that cannot render text — texting a customer the word "Array" is worse than a failed row an operator can read.
- `Listeners\DispatchBookingWebhooks` fans the booking lifecycle out automatically: `booking.created`, `booking.confirmed`, `booking.rescheduled`, `booking.cancelled`, `booking.completed`, and `booking.no_show`. Hung off the events rather than called from `BookingService`, for the reason the events exist — a booking can be confirmed by the widget, an admin screen, an importer, or a series materialising — and because a call inside the service would put the endpoint query, and on a `sync` queue the whole HTTP delivery, inside the advisory lock and transaction a booking write holds, where a slow consumer becomes a slot nobody else can book.
- The body is an envelope of `event`, `occurred_at`, and `data`, with the booking under `data.booking` so an event later carrying something beside it can add a key without moving the one every consumer already reads. Times go out in UTC as ISO 8601 with the customer's zone named beside them rather than applied to them; the service and provider are named as well as identified, because an integration writing "Consultation with Dana" into a CRM should not have to fetch two more records over an API to render one line.
- The site comes from the booking rather than from the ambient context, and `WebhookDispatcher::dispatch()` takes it as a third argument. These events are raised from console as well as from requests — a completion sweep, a series materialising overnight — and in console nothing has resolved a site, which leaves the global scope inert and every tenant's endpoints matching. One tenant's customer arriving at another tenant's CRM is the kind of bug that is found by the wrong person.
- `Services\WebhookDispatcher` and `Jobs\DispatchWebhookDelivery` per plan §5.2, §5.6, and §9.4 — outbound delivery to the endpoints subscribed to an event, with every attempt written to `booking_webhook_deliveries`. The ledger is the point: the questions asked about a webhook after the fact — what did you send, when, what came back, are you going to try again — are questions about state, and a consumer claiming an event never arrived is answered by showing them the body and the response code rather than by grepping a log.
- One row per endpoint per event, carrying its own attempt counter, updated in place by each retry. A delivery therefore reads as one thing that succeeded or died rather than as six unrelated attempts an operator has to assemble in their head.
- Requests are signed `HMAC-SHA256( "{timestamp}.{body}", secret )` with the endpoint's own secret, sent as `X-ArtisanPack-Signature: sha256=<hex>` beside `X-ArtisanPack-Timestamp`, `X-ArtisanPack-Event`, `X-ArtisanPack-Delivery`, and `X-ArtisanPack-Attempt`. The timestamp is *inside* the signed string rather than merely alongside it: a signature over the body alone is replayable forever by anybody who captured one request, and a consumer has no way to tell a replay from a retry. The JSON is encoded once and posted raw rather than handed to the client as an array to re-encode, because the signature is over the bytes that go out — two encoders disagreeing about a slash or a unicode escape produce a signature the consumer cannot reproduce.
- Retries run on `webhooks.delivery_backoff_minutes`, which is the list of delays *between* attempts rather than an attempt count, so the shipped 1/5/30/120/720 gives six attempts over about fourteen hours before the delivery is marked `dead`. Zero and negative entries are dropped rather than clamped: a zero would mean an immediate retry into an endpoint that has just failed, which is precisely the retry storm a backoff schedule exists to prevent.
- The schedule lives in the row rather than in the queue's own `backoff()`, and the job re-queues itself with the delay that row was given. A queue-side schedule would be less code but would keep the plan in a worker's memory of a job — an operator asking when a delivery will next be tried would have nothing to look at, an endpoint disabled mid-schedule would keep its pending retries alive inside the queue, and `failed_jobs` would fill up with entries for consumers being down, which is a thing that happens rather than an incident.
- Failures are counted on the endpoint rather than on the delivery, so an endpoint returning 500 to everything is disabled after `webhooks.failure_threshold` consecutive failures however those were spread across events; one success resets the count, because the threshold is for an endpoint that is gone rather than one that flapped. The increment is done in SQL and the threshold checked against what came back, so two workers failing at once cannot both read 9 and both write 10 — and `Webhook::disable()` settles the other half with a conditional update, so only one of them fires `WebhookDisabled`.
- A delivery aimed at an endpoint that has been disabled or deleted underneath it is killed rather than failed, and is not counted against the endpoint. Retrying into an endpoint that has already been given up on is exactly the queue traffic disabling it was meant to stop, and counting it would mean an endpoint switched off by an operator went on accruing failures for the crime of being off. A payload that will not encode is killed for the same reason from the other direction: the payload is stored rather than rebuilt, so there is nothing a retry would do differently, and the consumer did nothing wrong.
- Nothing in the delivery path throws. A refused connection, a 500, a name that no longer resolves, a TLS failure — every one of them is an outcome to write down rather than an error to take a queue worker down with, and `$tries` is 1 precisely so that a consumer being unreachable never becomes a failed job. Response bodies are truncated to 2,000 characters before they are stored, so an endpoint answering a webhook with an entire HTML page does not write that page into every row of the ledger.
- The job takes a delivery id rather than the model. The ledger is retention-pruned, so a queued job can outlive the row it names, and `SerializesModels` would turn that into a `ModelNotFoundException` and a failed job where an id that no longer resolves is simply nothing to do. Running the job twice is safe for the same class of reason: a delivery that is no longer retryable is left alone, so a redelivered job whose attempt already succeeded does not send the consumer the same event again.
- `webhooks.timeout_seconds` (10), `webhooks.connect_timeout_seconds` (5), and `webhooks.queue` (null) join the webhook configuration. The timeouts are short on purpose — a delivery is a notification, not a transaction, and a consumer taking half a minute to answer would otherwise hold a worker for every endpoint it is slow for — and the queue setting is for installations where a slow consumer must not delay anything else that is queued.
- Redirects are not followed, and the endpoint URL is documented as trusted input. Delivery posts wherever the row says from inside the application and stores the first 2,000 characters of the reply where an admin screen reads it, which is a request-forgery primitive when the URL is not trusted — an internal service or a cloud metadata endpoint is reachable from the server and not from a browser, and the response comes back out through the ledger. Refusing redirects keeps the address that was reviewed the address that is called; validating the address itself belongs to whoever builds the screen that accepts it, since a package cannot know which of its hosts' internal addresses are legitimate destinations. An installation exposing endpoint creation to anybody less trusted than an operator needs a scheme allowlist and a resolved-address check against private and link-local ranges, re-checked at delivery time.
- `illuminate/bus` and `illuminate/queue` are now required dependencies, since the package ships a queued job.
- Notifications per plan §5.6 and §10.2 — `BookingConfirmation`, `BookingReminder`, `BookingCancellation`, `BookingReschedule`, and `BookingNoShow`, delivered over a `mail` channel to the customer and a `database` channel to staff, orchestrated by `Services\NotificationService`. Times are rendered in the booking's `customer_timezone` rather than the application's: a customer in Auckland told the server's "09:00" misses their appointment, and would have been told the wrong thing by the confirmation, the reminder, and the reschedule notice alike.
- The order of operations inside a send is the design. Channels resolve from config and then through `ap.bookings.notification.channels`; the channel is asked whether it has anywhere to deliver; the notification is built and run through `ap.bookings.notification.sending`; **then** the log row is claimed; then it sends. The claim sits after the filters so a suppressed or unsupported send leaves nothing behind to block a later, real one — a channel switched off when the cron first ran must still send once it is switched back on — and before the send, because a claim taken afterwards is not a claim: two workers would both find nothing, both send, and both write a row.
- `Services\ReminderScheduler` and `bookings:send-reminders`, scheduled every fifteen minutes with `withoutOverlapping()`. A reminder is identified by the moment it was scheduled for — the start minus a configured number of hours — and that moment is the deduplication key, so two runs computing the same cadence claim the same row and exactly one sends. A run that finds a moment which passed while the cron was down still sends, because a late reminder beats no reminder; it will not send one after the appointment has started, which would be a reminder to attend something already under way.
- `channel` joins the notification log's unique key, which is now `(booking_id, type, channel, scheduled_for)`. The package sends one message over several channels at once, and keyed without it the first channel to claim locked the others out — the customer would get their email and the admin notification would silently never arrive. The `NotificationChannel` contract already documented the key as including the channel; the schema is what disagreed. Reminder idempotency is unaffected: a doubled cron still loses its second claim on each channel.
- `Contracts\NotificationChannel` gains `recipient()` and takes the notification in `send()`. Two of the hooks in the design-time spec filter a `Notification` instance, and a channel constructing its own would deliver an unfiltered message and silently discard whatever a subscriber did to it. The contract had no implementations yet, so nothing outside the package's own fixtures moved.
- Two implementations answer to the `database` channel, and the package picks between them. `artisanpack-ui/cms-framework` ships its own `notifications` table — auto-increment id, `title`/`content` prose — where Laravel's database channel wants a UUID key and a JSON `data` column, so the two cannot share it and the failure is the quiet kind: every insert errors, the row is logged failed, and staff never hear about a booking. Where cms-framework is installed the notice now goes through its notification centre instead, which is the better outcome on its own merits — one inbox for everything the CMS raises, the per-user preferences it already has, and its queued email — and the five lifecycle messages register as notification types so staff can switch off reminders without switching off cancellations. Standalone installations keep the Laravel-native channel.
- `notifications.database.driver` decides which: `auto` (the default) detects cms-framework, while `cms` and `laravel` force one — for an installation running the CMS admin shell that wants booking notices kept in Laravel's own table. Recipients come from a role under cms-framework, because a role stays right as staff join and leave while an id list goes stale the moment somebody does, and nothing notices.
- The reminder sweep reads across every site. It runs from cron, where nothing has resolved a site and the scope is already inert — but an application whose resolver answers in console too would have had this quietly sweep one tenant and leave every other customer without a reminder. Reading across sites is safe where writing across them is not: each reminder goes to the customer on the booking, with that booking's own details.
- The `database` channel refuses to guess who counts as an admin. There is no user table this package can assume and no role system it can query, so recipients come from `notifications.database.notifiable` and `.ids`, and the channel reports itself unsupported until they are set — an unconfigured installation emails the customer and writes no admin rows, silence being the better default over notifying the wrong people. It logs an internal reference such as `App\Models\User:12` rather than a staff address, so the erasure sweep that redacts `recipient` for a booking does not blank the record of who was told about it, and there is no staff address in that table to leak. It also forces Laravel's `database` channel rather than reading the notification's own `via()`, which is `mail` — routing the admin copy by that list would email every administrator the customer's appointment.
- A channel that throws is recorded as failed and the loop carries on. The caller is either a lifecycle transition that has already committed or a cron walking hundreds of bookings, and neither should be undone or abandoned because one channel is down; one dead SMTP host should not cost the admin their database notification. The row keeps its claim, so a retry cannot double-send, and `failed` rows are how a dead channel gets noticed.
- A channel named in config with nothing registered for it is skipped rather than fatal — `webhook` ships in the default config ahead of the ticket that implements it, and an install that has not caught up should still send its email.
- `Support\HookRegistry` — the canonical list of every hook the package owns, its type, and the issue that fires it, including the ones whose surfaces are not built yet. Hook names stay as literals at their call sites, which is how the rest of the ecosystem writes them and what keeps the name visible to whoever is reading the code that fires it; the registry is a catalogue rather than a source of names, and nothing in `src/` reads it. Payloads are documented as plain comments beside each entry rather than as docblock tags, because a docblock can only describe the thing it is attached to and php-cs-fixer enforces that by dropping the tags it cannot place — thirty hook signatures in one docblock came back from the formatter with every `@return` removed.
- The registry is held to the code by tests that assert it from both ends: every name declared shipped is fired somewhere in `src/`, every `ap.bookings.*` literal in `src/` is declared in the registry, and every shipped name appears in the README's table. So a surface cannot ship without its hook, a hook cannot ship undocumented, and a rename that misses a call site fails rather than quietly unsubscribing everybody.
- Hooks whose surfaces do not exist yet — calendar sync, notifications, reminder scheduling — are declared `pending`, and the same test asserts they are *not* fired. That is the half that fails loudly when a ticket ships a surface without its hook: firing one turns the suite red until somebody drops the flag, which puts them in front of the payload comment at the moment the payload becomes real.
- The retired plan §5.5 names are listed and asserted absent from `src/`, `tests/`, and the docs, alongside a shape check — `ap.`-prefixed, no snake_case — that catches the ones nobody thought to list. A subscriber written against a retired name binds cleanly and simply never fires, which is a failure nothing else in the suite would notice.
- `Support\HookSubscriptions` — the one place that answers whether an optional package is installed, for integrations that subscribe to another package's hooks. It probes for the class the integration itself needs rather than the package's service provider, so it also fails in the case where the provider is present but the feature has moved; and it gates the *callback*, so a closure naming absent classes is never entered rather than fataling wherever the upstream filter happens to be applied. Upstream hooks keep their upstream names — this package does not rename another package's hooks.
- The four notification hooks dropped their `pending` flag, which is the registry mechanism working as designed: firing one turned the suite red until the flag came off and the payload comment was checked against what actually ships. Fixing that also surfaced a bug in the retired-name test itself — it matched substrings, so the retired `bookings.notification.sending` reported the live `ap.bookings.notification.sending` as a violation of itself. The match is now anchored so a hook cannot be its own retired ancestor, and the retired list carries the name #19 actually names, `bookings.customer.confirmation.subject`, in place of a guess that collided.
- Site resolution is deliberately not among those subscriptions. It reaches this package through core's `SiteContext`, which is where `ap.cmsFramework.currentSite.resolve` is applied on behalf of the whole ecosystem — subscribing here as well would resolve the site twice and let this package disagree with every other one about which site a request is for.
- `Services\ManageTokenService` from plan §5.2 and §9.2 — the one place a manage token is minted, hashed, and checked. A manage token is the whole credential behind a public booking: there is no account, so the link in the confirmation email is what proves the person cancelling is the person who booked. `mint()`, `hash()`, `verify()`, `verifyFor()`, `findBooking()`, `issueFor()`, and `reissueAll()` are the whole surface, and `Booking::newToken()`, `Booking::hashToken()`, and `Booking::findByManageToken()` now delegate to it rather than carrying a second implementation of the same scheme.
- Tokens are 32 bytes of `random_bytes()` output rendered as 64 hex characters, and nothing about them is derived from the booking — a token encoding the reference or the customer's email would let somebody who knows one booking enumerate the rest. `bookings.manage_token_hash` stores `sha256(token)` and nothing else, so a leaked row, backup, or replica hands over a hash that cannot be turned back into a working link. A plain SHA-256 rather than a password hash is deliberate: the input is 256 bits of CSPRNG output rather than something a person chose, so there is no dictionary for a work factor to slow down, and a salted hash would rule out finding the booking by its hash at all.
- Comparison goes through `hash_equals()` rather than `==`, so a caller cannot learn a hash prefix by measuring how long a wrong token takes to be rejected — and cannot reach PHP's numeric-string juggling, where two `0e`-prefixed hex strings compare equal. The indexed lookup finds the candidate row; the constant-time compare is what decides the token is right, and `findBooking()` returns null when it is not.
- `bookings:reissue-detached-manage-tokens` rotates every token in every site, for when one has leaked. It is deliberately blunt — every manage link the package has ever sent stops working — and asks for confirmation unless given `--force`. Rows are rewritten through the base query builder, so `updated_at` is left alone rather than reporting every booking in the system as edited, and no model events fire, so the availability cache is not invalidated once per booking for a change that cannot affect availability. Chunking is by id rather than by offset, because the rows being paged over are the rows being rewritten and an offset walk over a moving target skips some of them — and a booking left on its old token is the one link the rotation was called to kill.
- `ap.bookings.manageTokenReissued` fires per rotated booking with its new plain token — the only moment it can be read — so an application with mail wired up can re-send the manage links as the rotation runs, and `ap.bookings.manageTokensReissued` fires once with the total. The per-booking hook carries a live secret by design; it is not for logging.
- `illuminate/console` is now a required dependency, since the package ships an Artisan command.
- `Services\SeriesService` from plan §5.2, §5.4, and §5.6 — recurring bookings, with the RRULE as the source of truth and the occurrences materialised from it. `create()`, `edit()`, `cancel()`, and `expand()` are the whole surface. Both halves are needed: without materialised rows the admin filters, the calendar push, and the reminder cron would each have to expand recurrence rules for themselves, and three implementations of RFC 5545 in one package is three chances to disagree about what a customer booked; without the rule, a "this and all following" edit could only approximate the arrangement by pattern-matching the rows it produced.
- The start is stored as a **floating** local date-time — a clock face plus the zone to read it in — rather than as an instant, and expansion runs in that zone and converts to UTC last. That is what makes the rule survive daylight saving: a customer who books a weekly 15:00 call means 15:00 every week, not the UTC instant that happened to be 15:00 in March, so the occurrences either side of a clock change land an hour apart in UTC and on the same clock face locally.
- Occurrences are written one at a time through `BookingService`, never directly, so every one of them goes through the slot lock, the availability check, the intake validation, and the `ap.bookings.*` lifecycle hooks exactly as a single booking does. A twelve-week series fires twelve `created` actions — once per booking that exists — and no more, which is asserted rather than assumed: the failure it guards against is a materialisation that re-fires the whole run's hooks per occurrence, and a series of twelve sending seventy-eight confirmation emails is not noticed until the mail bill arrives.
- Materialisation is deliberately **not** wrapped in a transaction. `BookingService::create()` dispatches `BookingRequested` after commit, which is where a listener gets to veto a booking by cancelling it, and an outer transaction would push every one of those listeners past the end of the whole materialisation — so they would be cancelling confirmed bookings rather than preventing them. It also means a slot lost in week seven costs week seven rather than the series.
- An occurrence whose slot has gone is skipped rather than fatal. A rule expanded over months will cross somebody's holiday sooner or later, and refusing the whole arrangement over week seven serves nobody; `SeriesCreated` carries how many were actually booked, so a caller comparing it against `expand()` can tell the customer which weeks did not land. The series index advances across the gap rather than renumbering around it, so week eight does not quietly become week seven. Only a rule where *nothing* could be booked is refused, and that path removes the series row it had already written — a series with no occurrences shows up in the admin list as a recurring booking whose appointments nobody can find.
- A series is pinned to one provider. Recurring means the same person: a weekly 1:1 that round-robined a different coach each week would be a different product. A caller who names a provider gets them for every occurrence; a caller who does not gets the rota's answer for the first, written back onto the series so every later occurrence and every re-materialisation follows it.
- The three edit scopes from `Enums\SeriesEditScope`, each doing something genuinely different to the data. `this` detaches a single occurrence and leaves the rule alone; `this_and_following` bounds the original rule just before that occurrence — rather than rewriting it, so everything already delivered stays described by the rule it was actually booked from — and carries the change forward on a new series that inherits the original's own upper bound; `all` rewrites the rule and re-derives everything still to come. Occurrences that have already started are never rewritten, because that would be a claim about the past nobody made, and detached ones are never re-materialised, because detaching *is* the record that the rule no longer describes them.
- `cancel()` is the one place a detached occurrence is not left alone. Somebody moving one week to a different afternoon does not make it any less part of the arrangement being called off, so every future occurrence goes, detached or not — while the ones that already happened stay exactly as they are.
- The series bound and the rule bound are both honoured, with the earlier winning. `Recurr\Rule::setUntil()` clears `COUNT`, so a series that says "twelve times" and "not past December" cannot push its bound into the rule without losing the twelve; the upper bound is applied to the expanded instants instead, which is the reading somebody looking at both columns would expect. Expansion is additionally capped by `artisanpack.bookings.series.max_occurrences`, which is what stops an unbounded `FREQ=DAILY` from asking for an unbounded number of rows.
- `occurrence_count` records only the count the *rule* declares, and stays null for an `UNTIL`-bounded or unbounded rule. Filling it in from the expansion would make a column meaning "what the rule says" quietly start meaning "what we managed to book this time".
- The intake answers, the notes, and the customer's zone are read back from an occurrence the series has already produced when it is re-materialised. None of them are columns on the series, so there is nowhere else they survive — and without it an "all" edit would hand the provider a fortnight of bookings with the intake form blank. The tail of a split reads them from the head, which is the only series that has any.
- `ap.bookings.series.editApplying`, per the design-time hook spec in #53, firing once per scoped edit before any of it lands — so a subscriber reading the series back still sees the rule it is about to replace. The scope is passed as the string `this` / `this_and_following` / `all`, matching what `SeriesEdited` carries and what an admin form posts, rather than as the enum.
- `Exceptions\SeriesException`, separated from `SlotUnavailableException` because none of its cases get better by retrying: an unparseable rule, a rule that names no occurrences, an occurrence handed to the wrong series, a scope asked to work without the occurrence it is named after, a series cancelled twice. A widget offering "pick another time" in response to a malformed RRULE is telling the customer something untrue about their own request. The wrong-series case in particular is refused loudly rather than ignored — a split keyed off the wrong occurrence would bound one arrangement at a date taken from another and cancel the wrong customer's appointments.
- Rule-touching edits read an allow-list of series columns from `$changes` rather than filling the model. `$changes` reaches the service from an admin form, and the columns it must not carry — `site_id`, `pii_erased_at`, `cancelled_at`, the primary key — are exactly the ones a request has no business setting. A single-occurrence edit reads a booking-column allow-list on the same grounds, with `start_time` deliberately absent from it: moving an occurrence goes through `BookingService::reschedule()` so that it takes the slot lock and fires the reschedule hooks, rather than being written over the top of whoever else is holding the new time.
- Edits run pinned to the series' own site rather than to whichever site happens to be in context, via core's `SiteContext::forSite()`. An edit reads and writes far more than the series row — it looks the service up, cancels occurrences, and materialises new bookings, each of them site-scoped on the way in and site-stamped on the way out — and the two paths the package supports for crossing sites, a console command looping with `forSite()` and a maintenance query using `acrossAllSites()`, both leave the ambient site disagreeing with the series being edited. Unpinned, such an edit either writes the tail of a split, carrying that customer's name, email, and phone, under a tenant they do not belong to while hiding their forward bookings from the tenant that owns them; or it fails halfway, because the service it needs is invisible from where it is standing, leaving the head bounded and its occurrences cancelled with nothing put in their place. A null site pins "no site", which is the inert state a single-tenant installation already runs in.
- Both rewriting scopes free the old slots before taking the new ones, which is the only order that lets a rule keep times it already holds. A rule that cannot be *read* is refused before anything is cancelled, so a typo in the RRULE leaves the arrangement standing; a rule that reads fine but books nothing throws `SlotUnavailableException`, because returning an empty arrangement the caller would take for a working one is worse than saying so. Individual weeks that cannot be booked are still skipped rather than fatal — only losing all of them counts as failure.
- A `this_and_following` split divides a `COUNT` between the two halves instead of handing it to both. The tail starts a fresh `dtstart`, so an inherited `FREQ=WEEKLY;COUNT=12` would begin counting to twelve again — and a twelve-week package moved from week five would quietly become sixteen sessions, invoiced or not. A caller supplying their own `rrule` is redefining the arrangement rather than continuing it, and is left alone.
- A split at the very first occurrence cancels the head rather than bounding it. There is nothing before the split to keep, and an `UNTIL` a second before its own `DTSTART` is a rule that names nothing — which would leave the head permanently unexpandable and every later edit of it throwing.
- `edit()` refuses a series that has been cancelled. The way in is ordinary — an admin with the edit form already open when the customer cancels it themselves — and without the guard the series goes on reporting itself cancelled while carrying live confirmed bookings, so the provider gets appointments for an arrangement every screen says is off.
- A `create()` that fails partway removes the occurrences it had already written, and removes them before the series row. `bookings.series_id` is `nullOnDelete`, so deleting the series first strands them: the database nulls the key without Eloquent ever running, the rows keep a `series_index` for a series that no longer exists — the state `Booking::booted()` exists to prevent — and, worse than untidy, they go on holding their providers' slots for an arrangement the caller was told did not happen. They are hard deleted rather than cancelled, because nothing was returned to the caller and no confirmation went out, so a cancelled row would put a phantom in the customer's history.
- Every occurrence records how its provider was really chosen. Each one after the first names the provider the series is pinned to, which puts `BookingService` on its "the caller chose this provider" branch, where the recorded strategy defaults to `customer` — so eleven weeks of a twelve-week rota-assigned series would have claimed the customer picked, in a column documented as saying how the booking got its provider.
- A single-occurrence edit moves the booking before it detaches or rewrites anything. The move is the only part that can fail — somebody else can take the new time between the widget rendering it and the form arriving — and doing it first means a lost race changes nothing at all, rather than leaving the occurrence detached and its notes rewritten while it sits at the time it always had, invisible to every later rewrite of the rule and with no `SeriesEdited` to say so.
- `ap.bookings.series.editApplying` fires inside the site pin rather than outside it, so a subscriber reading the series back does so under the series' own site. A `fresh()` from the wrong site returns null, and a subscriber written against the documented payload would fatal on it.
- Test coverage for the whole surface: expansion including the daylight-saving case and both bounds, materialisation and its ordering, provider pinning, the skipped-slot gap, all three edit scopes with their splits and their re-derivations, the detached-occurrence guarantees under `all` and under `cancel`, the site pinning and its restoration, rollback when either rewriting scope is handed an unreadable rule, the events and their payloads, and a fire-count assertion proving a series of four fires four `created` actions rather than sixteen.

- `Services\BookingService` from plan §5.2 and §5.8 — the single place a booking's whole life is decided. `create()`, `confirm()`, `reschedule()`, `cancel()`, `complete()`, and `markNoShow()` are the only supported ways to move a booking between statuses, and that is a rule rather than a convention: nine lifecycle actions and six domain events hang off these transitions, and the guarantee every listener downstream is written against is that each fires exactly once per transition. A manage-token route or an admin screen flipping a status itself would either fire nothing or fire it twice, and both failures surface a long way from the code that caused them.
- Race safety in three layers, all of which are needed. The advisory lock decides the ordinary case before either request reaches the database; the partial unique index on `bookings` settles the case where the lock was never held — a write from code that did not take one, a process that died holding it, a second application server on a cache with no shared locks; and the round-robin assigner falls through to the next free provider when the index refuses an insert, so a customer who lost the race gets the colleague who is also free rather than an error page. `create()` throws `SlotUnavailableException` only once every candidate has lost.
- The slot lock buckets by the provider's **local day** rather than by the start instant, which is a deliberate departure from plan §5.8. Keying on `(provider, start time)` is only sufficient when no two bookable slots overlap, and they routinely do: at the default fifteen-minute interval a sixty-minute service offers a slot every quarter hour, each overlapping the last three. Two customers taking 09:00 and 09:15 would hold different locks, neither would see the other's uncommitted row, and the partial unique index would accept both because it keys on the start time and the two starts differ — a provider double-booked for forty-five minutes from an entirely ordinary pair of requests. A day is the smallest bucket wider than anything booked inside it, and the local day is the right one because a working day does not straddle its own midnight. The cost is that one provider's bookings for one day serialise, and a provider is one person.
- An overlap check inside the lock, alongside the resolver's answer and the index. Each of the other two is narrower than the invariant: the resolver is read through a cache a competing commit on another machine may not have reached, and the index refuses only an identical start time, so a booking landing in the *middle* of one already there satisfies both. The day lock is what makes the check decisive — nobody else can be writing to that provider's day while it runs.
- `Services\ProviderSlotLock`, keyed on a hash of `(provider_id, provider-local date)` — two callers holding the same moment in different zones are contending for the same provider-day, and a bucket read off the caller's clock face would give them different locks and let both through. Postgres takes `pg_advisory_xact_lock` and lets the server release it at commit, because the thing most likely to forget to let go is a fatal error; MySQL has only session-scoped `GET_LOCK`, so the release is explicit and lives in a `finally` after the transaction rather than inside it — releasing early would hand the slot to the next waiter while this booking was still uncommitted, which is the exact window the lock exists to close. Everything else falls back to the cache store's lock, which is a weaker guarantee across machines and an honest one within a process, so the sqlite suite exercises the same code path a real deployment does.
- Lock waits are bounded on every engine and report the same exception. `lock_timeout` is set `LOCAL` on Postgres and its SQLSTATE 55P03 is translated to `SlotLockTimeoutException`; MySQL passes the timeout to `GET_LOCK`; the cache path catches Laravel's `LockTimeoutException`. That is deliberately a different exception from `SlotUnavailableException` — one means the slot is gone and must not be retried, the other means nobody managed to find out and can be. Telling a customer their slot was taken when the truth is that a lock waiter timed out is a lie the domain should not be able to tell.
- A cache store that cannot issue locks throws rather than running unserialised. Every store Laravel ships implements `LockProvider`, so this can only come from an application's own driver — and it is the case that matters most, because on an engine with no advisory lock the cache lock is the only thing serialising two customers after the same slot. Silently degrading would look fine right up until two bookings landed in one slot on a busy afternoon.
- `Strategies\LeastRecentlyAssignedStrategy`, bound as the default `Contracts\RoundRobinStrategy`. The cursor is `round_robin_last_assigned_at` — a timestamp rather than a position — which is what makes the rotation survive the things that actually happen to it: a provider added halfway through the week, one deactivated for a month, a candidate list that differs slot by slot because everybody has their own hours. A positional cursor has to be told about all of that; "whoever has waited longest" answers it by construction. Never-assigned providers sort first, so somebody added today does not wait behind the entire history of the rota; ties break on `round_robin_weight` descending and then on id, so the same inputs always give the same answer and a lost race retries deterministically. The cursor moves inside the lock, alongside the booking, so a provider is never credited with work whose insert then rolled back.
- Sorting happens in PHP rather than in SQL. The candidate list has already been narrowed to providers genuinely free for the slot — which takes availability rules, overrides, buffers, and external busy blocks no `ORDER BY` can see — and `ap.bookings.availableProviders` may have changed it again since. Going back to the database to order what is already in memory would either re-fetch a set that no longer matches or silently drop whatever a subscriber added.
- `Services\IntakeFieldValidator` from plan §5.10, with `publish()`, `schemaFor()`, and `validate()`. Every method takes the schema *version* rather than reading the service's current form, because validating last year's answers against this year's is how a booking gets rejected for missing a question nobody was ever asked. `publish()` derives the next version from the recorded history rather than from the service's pointer — a service seeded at version 1 with no version row behind it would otherwise publish its first edit as version 2 and leave version 1 permanently unreadable for every booking already taken against it — and writes the row and moves the pointer in one transaction, since a service pointing at a version that was never recorded takes every booking made against it with it.
- Answers to fields the schema does not name are dropped rather than stored. `intake_data` is written from a public request onto a table an administrator reads back, so accepting whatever arrives would make the column an unvalidated dumping ground reachable by anybody who can reach the widget. Errors come back as a `MessageBag` on `IntakeValidationException` so a form can put each complaint beside the field it belongs to. A field type the package has not heard of validates as plain text rather than throwing — an administrator adding one should get a booking that works, and a field's own `rules` entry is where they say more. A choice constraint on a multi-answer field is applied to each answer rather than to the array holding them, because `in:` against an array never matches and would refuse every correct multi-select answer too.
- The nine booking lifecycle hooks from the design-time spec in #53 — `ap.bookings.creating`, `created`, `confirmed`, `rescheduling`, `rescheduled`, `cancelling`, `cancelled`, `completed`, and `noShow` — plus the `ap.bookings.availableProviders`, `ap.bookings.roundRobin.selectProvider`, and `ap.bookings.intakeSchema` filters. Each ships with a test proving a consumer-registered callback runs and, for the filters, that its return value is honoured and that a subscriber returning the wrong shape throws rather than silently producing a corrupt result.
- `ap.bookings.creating` fires inside the lock and can fire more than once per `create()` call, once per provider tried, while `created` fires exactly once. That asymmetry is the point: the first is "about to write this booking against this provider", which can genuinely be attempted twice, and the second is "a booking exists", which cannot. Neither is cancellable — a veto inside a held lock would run arbitrary third-party code with a slot locked — so cancellation stays with the `BookingRequested` event, which fires once the row exists and cancels for real, freeing the slot. `create()` re-reads the booking afterwards and declines to confirm one a listener has just cancelled.
- `ap.bookings.roundRobin.selectProvider` reads `null` as "no opinion" and leaves the rota's own answer standing, rather than as "nobody". The alternative reading would make an unconditional `return null` guard — the natural way for a subscriber that only cares about one service to stay out of the way — turn every unrelated booking unbookable. Returning a provider who was not among the candidates throws: they were not free for the slot, so honouring it would double-book somebody. The filter does not fire at all when the customer named their provider by hand, because "the package is about to decide" is not what happened.
- `Service::bookableProviders()`, with `AvailabilityService::providersFor()` delegating to it. Availability resolves slots for these providers and booking assigns one of them, and a second copy of "which providers count" would eventually disagree — at which point the widget offers a slot the booking path then refuses, for a reason visible from neither side.
- `Exceptions\BookingException` and its four subclasses, so a caller can tell "the domain refused this" from "something went wrong" without enumerating subclasses that do not exist yet.
- `create()` refuses a booking with a blank customer name or email. The columns are NOT NULL, which sounds like enough and is not: an empty string satisfies the database and produces a booking whose manage link goes to an empty address, whose reminder goes nowhere, and which no search an administrator would think to run will ever surface. Nothing later in the lifecycle can recover from it, so it is refused at the point the caller can still do something about it.
- `artisanpack.bookings.lock` (`wait_seconds`, `store`) and `artisanpack.bookings.auto_confirm` configuration. Switching automatic confirmation off is safe: a `requested` booking already holds its slot, so nobody else can take the appointment while somebody approves it — it only delays the confirmation email and the calendar push.
- `reschedule()` deliberately does not re-ask the resolver whether the new time is offered. It cannot usefully: the booking's own row is what makes its current time look taken, so availability computed around a booking being moved reports the move as a clash with itself and every half-hour shift becomes impossible. The caller decides which times to offer — that is what the resolver is for — and this enforces the invariant the caller cannot, checking for an *overlapping* active booking rather than a matching start, since a reschedule can land in the middle of an appointment rather than on top of one, which the unique index would let through.
- The insert inside the lock runs in a nested transaction, which on every engine is a savepoint. Postgres aborts an entire transaction on any failed statement, so without it the unique violation the round-robin retry is built to catch would poison the retry it exists to enable.
- Test coverage for the whole surface: provider choice, rotation fairness, cursor movement, the staged lost race and its fall-through, exhaustion of every candidate, intake snapshotting and refusal, all five lifecycle transitions with their events, and every invalid transition. The lock is proven on MySQL and Postgres against a second connection — which is what a second PHP worker actually is — for exclusion, release after both success and failure, and for *not* blocking a different provider or a different hour, since serialising more than the one contended pair would turn a busy diary into a queue.

- The public domain surface from plan §5.1 and §5.4 — the contracts under `src/Contracts/` and eleven new events under `src/Events/`. These are the names `artisanpack-ui/crm` will subscribe to, so they are treated as public API from the moment they land rather than from the moment something uses them.
- `Contracts\SlotResolver`, `RoundRobinStrategy`, `CalendarSyncDriver`, and `NotificationChannel`. Each is a seam an application binds its own implementation into: what counts as a free slot, who gets assigned to it, how one external calendar is talked to, and how one message is delivered. The docblocks carry the rules the callers rely on and cannot enforce — a sync driver's writes have to be idempotent because a timed-out push is indistinguishable from a slow success, and both drivers and channels have to throw on failure because a quiet return leaves a connection looking healthy while it has silently stopped working.
- `Contracts\SiteResolver` was deliberately *not* added. `artisanpack-ui/core` already owns that contract ecosystem-wide, and a second one in this namespace would let an application be site 2 for one package while being site 1 for another — the exact failure core's single-resolver design exists to prevent. Plan §5.1 lists it because it predates core 1.3.
- `Contracts\MeetingType` and `Contracts\MeetingTypeRegistry`, with `MeetingTypes\MeetingTypeRegistry` behind them and bound as a singleton. The four built-in types — `one_to_one`, `group`, `recurring`, `round_robin` — are registry entries rather than arms of a match statement, so an application adding a fifth does the same thing the package does instead of patching around it. Keys are snake_case rather than the plan's `1:1` / `round-robin` prose spellings, because a key is a stored value and every other stored identifier in the package is snake_case. Labels and descriptions are held untranslated and run through `__()` when they are read rather than when the type is constructed — the registry is a singleton, so translating eagerly froze every label at whichever locale happened to be active the first time anything resolved it, which an Octane process or a queue worker serving more than one locale outlives.
- The `ap.bookings.registeredMeetingTypes` filter, per the design-time hook spec. It runs on every read rather than once at boot, so a package registering a type from its own service provider does not have to know whether it boots before or after this one. Filtered entries are re-keyed from each type's own `key()`, so appending with `$types[] =` and assigning to a key behave identically and a type cannot end up registered under a key that disagrees with the one it reports. A subscriber returning a non-array, or an entry that is not a `MeetingType`, throws rather than silently producing an empty or corrupt registry.
- `Events\BookingRequested`, `BookingConfirmed`, `BookingRescheduled`, `BookingCancelled`, `BookingCompleted`, `BookingNoShow`, `SeriesCreated`, `SeriesCancelled`, `SeriesEdited`, `CalendarSynced`, and `CalendarSyncFailed`, joining the existing `CalendarConnectionDisabled` and `WebhookDisabled`.
- `Enums\BookingActor` and `Enums\SeriesEditScope`, both of which exist because the row alone cannot answer the question a listener needs answered. "The customer cancelled" and "we cancelled on the customer" are the same status change and completely different events downstream; a one-off change to a recurring series and a rewrite of the whole arrangement are the same edit and completely different events downstream.
- `Support\TimeRange` and `Support\Slot`, the payload types the contracts are stated in. `TimeRange` is half-open — `[start, end)` — so back-to-back bookings are legal while a genuine double booking is not, and every overlap question in the package is asked of it so the answer cannot differ between two call sites. Endpoints are normalised to `CarbonImmutable`, so a caller that later mutates the Carbon it passed in cannot reach back into a range it already built.
- Event payloads are `readonly`, so the immutability the CRM package will depend on is enforced by the engine rather than by convention — one listener cannot rewrite what the next one sees. This survives the queue: `ReflectionProperty::setValue()` initialises an *uninitialised* readonly property through `zend_update_property_ex()` under the declaring class's scope, which is the same code path on every PHP the package supports, and a promoted property reports `hasDefaultValue() === false`, so `SerializesModels::__serialize()` never skips one and leaves it uninitialised on restore.
- Every event implements `ShouldDispatchAfterCommit`. Plan §5.8 writes bookings inside a transaction and behind an advisory lock, and `SerializesModels` restores a payload by re-reading it from the database — so an event that escaped mid-transaction could reach a queue worker on another connection before the commit landed, and the listener would die with a `ModelNotFoundException` on a booking that does exist. The interface is inert outside a transaction, and it is on the two pre-existing events too, because a dispatch guarantee that holds for eleven of thirteen events is not one anybody can rely on.
- The concrete `MeetingTypes\MeetingTypeRegistry` is aliased to the contract, not just bound behind it. Its constructor takes no arguments, so leaving it unbound let the container quietly auto-build a *second*, empty registry for anyone type-hinting the shipped implementation — losing every PHP-side registration at the call site most likely to be written by somebody reaching for the obvious class.
- `Support\TimeRange::toArray()` normalises to UTC. The endpoints are instants, so the construction zone carries no information the range is entitled to keep — but leaving it in made the serialized text differ between two call sites meaning the identical span, which matters the moment one is stored, sent to an external calendar, or compared as a string. The zone a customer chose lives on the booking, in `customer_timezone`.
- `MeetingTypes\RegisteredMeetingType` falls back to the source string when `__()` hands back something that is not one. `__()` is typed `string|array|null`, a language file may legitimately map a key to an array of lines, and returning that from a method declared `: string` would raise a `TypeError` inside the package for a mistake made outside it.
- `SeriesCancelled` rejects a negative occurrence count. Zero is legitimate — a series whose remaining occurrences had each been cancelled individually — but a negative one reaching a refund listener that multiplies by it moves money the wrong way.
- `SeriesCancelled::$cancelledOccurrenceCount` is required rather than defaulting to zero. The billing and refund listeners the count exists for cannot distinguish a caller who omitted it from a series that had nothing left to cancel, and silently refunding nothing is a worse outcome than a `TypeError` at the call site.
- `CalendarSyncFailed` carries the failure as a message rather than the `Throwable`. Exceptions do not reliably survive the queue — a worker can be handed one whose class is not loadable, or one holding a live database connection — and every event in this set has to.
- Test coverage for the whole surface: every event is dispatched, asserted on, delivered to a registered listener, and round-tripped through `serialize()`/`unserialize()`, since a payload that cannot make that trip fails only in production on a queue worker. Each contract has a plausible application-side implementation under `tests/Fixtures/` proving it is implementable and exercising the rules the docblocks state. The meeting-type filter is covered for adding, replacing, removing, late registration, key disagreement, and both refusal paths.
- The initial migration set — all sixteen tables from plan §4.2, in dependency order: `services`, `service_blackout_dates`, `service_providers`, `service_provider_service`, `availability_schedules`, `availability_overrides`, `booking_series`, `bookings`, `booking_calendar_connections`, `booking_calendar_events`, `booking_calendar_watch_channels`, `booking_webhooks`, `booking_webhook_deliveries`, `booking_notification_log`, `booking_intake_schema_versions`, and `booking_calendar_busy_blocks`. Loaded by the service provider rather than published, so an upgrade that adds a table lands on `migrate` without anybody re-publishing; the `bookings-migrations` tag exists for applications that need to edit the schema.
- The partial unique index guarding a provider's slot — `bookings(provider_id, start_time)` where the status is `requested` or `confirmed`. It is the backstop behind the advisory lock from plan §5.8: if the lock is bypassed, lost, or the write arrives from somewhere that never took it, the second insert fails and the caller retries with the next round-robin candidate. It has to be partial rather than a plain unique, because a plain one would also refuse a customer rebooking a slot they had previously cancelled, which is not a race.
- MySQL has no partial indexes, so the same rule is emulated there with a `VIRTUAL` generated column that evaluates to a slot key while the booking is active and to `NULL` otherwise — MySQL treats `NULL`s as distinct in a unique index, so inactive rows stop competing for the slot for the same reason the `WHERE` clause excludes them on Postgres and SQLite. Unassigned bookings fall out on every engine too: `NULL` columns leave a unique index, and `CONCAT()` with a `NULL` yields `NULL`. An unassigned booking is not holding anybody's slot.
- A second unique index making service and provider slugs unique among rows belonging to no site. `UNIQUE(site_id, slug)` alone says what it means only while a site is resolving: nulls are distinct in a unique index on every supported engine, so on a single-tenant installation — where `site_id` is null on every row, and which is the default configuration — it enforces nothing whatsoever. The plan's "unique per `site_id`" silently excluded the commonest case. Postgres and SQLite index the `site_id IS NULL` predicate directly; MySQL gets the generated-column emulation again. Soft-deleted rows stay in both indexes deliberately, because freeing a trashed slug lets a new row take it and then collide the moment somebody restores the old one — a worse failure than being told up front that the slug is taken.
- `UNIQUE(booking_id, type, scheduled_for)` on `booking_notification_log`, which is what makes the reminder cron idempotent by construction. Sending the 24-hour reminder becomes a claim on a row rather than a decision made by reading, so an overlapping cron, a queue that delivers twice, or a retry after a timeout all race to insert the same key, exactly one wins, and the losers fail cleanly instead of emailing the customer again. `scheduled_for` is null for unscheduled sends, and nulls are distinct in a unique index on all three engines — so two reschedules still produce two emails, which is right.
- Soft deletes and `pii_erased_at` on `services`, `service_providers`, `booking_series`, and `bookings`. The two are not the same thing: a soft delete hides a row while keeping the audit trail, and `pii_erased_at` records that the personal fields on a row that still has to exist were actually cleared.
- Per-engine migration coverage on SQLite, MySQL, and Postgres from one shared definition (`defineBookingMigrationTests()` plus `Tests\Concerns\AssertsBookingSchema`), covering table creation, site-scoping columns, erasure columns, index shape, rollback, and every branch of the slot guard and the notification-log key. Sharing the definitions is the point — the slot guard is two different mechanisms reaching for one rule, so a divergence has to surface as one engine's file failing rather than as a case somebody only ever wrote for SQLite. Each expected-failure insert runs inside its own transaction, because Postgres aborts a transaction on any failed statement and the surrounding test is already in one.
- Package scaffold generated from `package-blueprint`, following `artisanpack-ui/rbac` for the config layout and `artisanpack-ui/pagespeed-insights` for the provider and test conventions.
- `composer.json` — `ArtisanPackUI\Bookings` PSR-4 namespace, `php ^8.2`, `illuminate/support|database|http|notifications ^10.0|^11.0|^12.0|^13.0` (Laravel 13 requires PHP 8.3+ of its own accord, so on PHP 8.2 Composer resolves Laravel 12 or below — the two constraints resolve together rather than conflicting), and required `artisanpack-ui/core`, `artisanpack-ui/hooks`, `artisanpack-ui/security`, `artisanpack-ui/icons`, `nesbot/carbon`, `simshaun/recurr`, and `sabre/vobject` dependencies. `sabre/vobject` is a hard dependency rather than a suggestion because the outbound `.ics` feeds and the CalDAV driver both need RFC 5545 serialization we are not going to hand-roll.
- `suggest` entries for `artisanpack-ui/cms-framework`, `livewire-ui-components`, `forms`, `media-library`, `google`, `microsoft`, `apple`, and `accessibility`. Every one of these is soft: the package has to stay usable in a plain Laravel app, a headless API, or a widget embedded in a site that runs no ArtisanPack CMS at all.
- `Providers\BookingsServiceProvider`, auto-discovered by Laravel, with the `bookings` singleton binding.
- `config/artisanpack/bookings.php` covering timezone, slot interval, availability cache, booking window, cancellation, series, notifications, calendar sync, webhooks, admin and public surfaces, retention, and multi-tenancy. Published under the `bookings-config` tag to `config/artisanpack/bookings.php`, and merged under the matching `artisanpack.bookings` key. Laravel's config loader (`LoadConfiguration::getNestedDirectory`) prefixes keys with the nested directory name, so a published file at that path loads under `artisanpack.bookings`; `mergeConfigFrom` is handed the same key explicitly to match. A bare `bookings` key would have left applications editing a published file the package never reads.
- Every calendar driver ships disabled and `calendar.default_sync_mode` is `outbound`. Two-way sync stays opt-in per connection because it hands an external calendar the power to suppress availability.
- Code style toolchain — `pint.json`, `.php-cs-fixer.dist.php`, and `phpcs.xml`, all three covering `config/` alongside `src/` and `tests/`, with `lint`, `fix`, `cs`, `cs:fix`, and `test` composer scripts. `pint.json` is generated from `artisanpack-ui/code-style-pint`'s `ArtisanPackUIPreset` with five Laravel-preset rules turned off: `phpdoc_no_package` and `no_superfluous_phpdoc_tags` strip the `@package`/`@subpackage`/`@param`/`@return` tags the house PHPDoc standard requires, and `declare_parentheses`, `trim_array_spaces`, and `no_spaces_around_offset` strip the WordPress-style spacing PHP-CS-Fixer's custom fixers add. Left on, Pint and PHP-CS-Fixer would have reformatted each other on alternate runs; `composer fix` now runs Pint first and settles the spacing with PHP-CS-Fixer, and both report clean on the result.
- Pest + Orchestra Testbench setup with a base `TestCase` and coverage of the boot, binding, facade, helper, publish-tag, and config-default paths. The test application registers the core, hooks, and bookings providers and runs against sqlite `:memory:`, and model factories resolve to `ArtisanPackUI\Bookings\Database\Factories\<Model>Factory` — Laravel's default guess looks under `App\Models` and would never find a package factory.
- `Tests\Concerns\TestsWithSqlite`, `TestsWithMysql`, and `TestsWithPostgres`, with matching `mysql` and `postgres` Pest groups and `composer test:sqlite`, `test:mysql`, and `test:postgres` scripts. Booking creation has to be race-safe and the guard is a named advisory lock — MySQL's `GET_LOCK`, Postgres' `pg_advisory_xact_lock` — which sqlite has no equivalent for, so those tests need a real server. They skip when one is unreachable, so `composer test` stays green on a machine with no database running; CI sets `BOOKINGS_REQUIRE_EXTERNAL_DB=1`, which turns the skip into a failure, because a skipped lock test otherwise reads as "race-safety verified" while verifying nothing. `test-mysql` and `test-postgres` jobs run both engines against service containers, and the sqlite matrix excludes the two groups. Harness coverage proves the lock is exclusive across two connections on each engine and that factory names resolve into the package namespace.
- Site resolution comes from `artisanpack-ui/core` (`^1.3`): models scope on whatever `ArtisanPackUI\Core\MultiTenancy\SiteContext` reports, and this package binds no contract, resolver, or configuration block of its own. One place decides which site a request is for, so an application installing several ArtisanPack packages cannot be site 2 for analytics while being site 1 for bookings. Site scoping is switched on in `artisanpack.core.multi_tenant.enabled`, resolvers are listed in `artisanpack.core.multi_tenant.resolvers`, and work that has to target a specific site pins one with `SiteContext::forSite()`.
- `Models\Scopes\BelongsToSiteScope` and the `Models\Concerns\BelongsToSite` trait that opts a model into it — named as a pair after Laravel's own `SoftDeletes`/`SoftDeletingScope`. The scope qualifies `site_id` with the table name so it survives a join, and the trait stamps new records with the site in context unless one was set explicitly. `acrossAllSites()` lifts the scope for maintenance queries such as retention pruning that deliberately span every site. An explicitly set site beats the resolved one, so that deliberate cross-site writes stay possible — which means `site_id` has to stay out of every owning model's `$fillable`, or request data could place a row under another tenant. That rule is documented on the trait and locked in by a test.
- Feature coverage for the multi-tenancy scaffolding: a booking under one site is invisible to a query scoped to another; every row stays visible while site scoping is disabled, when core's shared context is not bound, and when the resolver reports no site; a non-numeric string site identifier scopes and stamps correctly; and a site pinned through `SiteContext::forSite()` scopes queries and stamps writes even while scoping is switched off, which is what a console command looping over sites depends on.

### Changed

- The booking status the specification calls `pending` is `requested`. Plan §5.8 names the slot guard's predicate as `status IN ('requested','confirmed')`, and having the index and the enum disagree about what an unconfirmed booking is called is the kind of thing that is discovered by a race nobody can reproduce. The enum is `requested`, `confirmed`, `cancelled`, `completed`, `no_show`.
- The slot guard also excludes soft-deleted rows, which is one step beyond plan §5.8. A soft-deleted booking is invisible to every domain query, so leaving it in the index would block a slot availability reports as free — and produce a unique violation no retry could resolve, because no candidate provider is the problem. The index has to agree with what the model can see.
- `site_id` is on the seven tables plan §4.3 gives it to, not on all sixteen. The other nine hang off one of those — a busy block belongs to a connection, a schema version to a service, a delivery to a webhook — so they are already reached through a scoped parent. A second copy of the same fact would only add somewhere for it to disagree, and §4.3's per-table schema is the more specific statement of §4.1's rule.
- `availability_overrides` carries an explicit `type` enum (`unavailable` / `custom_hours`) rather than the specification's `is_available` boolean. That boolean had to mean two different things at once — "blocked" and "these hours instead" — and reading a schema should not require knowing which.
- The pivot is `service_provider_service`, per plan §4.2, rather than the specification's `service_provider_services`. Laravel's convention derives a pivot name from the singular models in alphabetical order, so the plan's name is the one the framework will guess without being told.
- `bookings` and `booking_series` restrict deletion of the service and provider they reference rather than cascading or nulling. Both parents are soft deletable, so a hard delete is an explicit destructive act, and letting one silently take every booking ever made against it is the worst outcome available — retention pruning clears the children first and then the parent goes. The `series_id` link is the deliberate exception and still nulls: losing the rule that generated a set of occurrences should not lose the occurrences.
- `services.default_provider_id` and `service_providers.user_id` are indexed but carry no foreign key. `default_provider_id` points at a table created two migrations later and adding the constraint afterwards would need an `ALTER TABLE` SQLite cannot express without rebuilding; `user_id` points at the host application's users table, which a package cannot assume exists or knows the key type of. Same reasoning for `image_media_id` and `oauth_connection_id`, both of which point into suggested packages that may not be installed.
- `security` and `icons` are required at `^2.0`, not the `^1.0` written in plan §3.1. Both packages shipped a 2.x major after the plan was written, and `^1.0` would have pinned bookings to a superseded major — and failed to install alongside the rest of the ecosystem, which is already on 2.x.
- The site-resolution filter is named `ap.cmsFramework.currentSite.resolve`, not the `cms.current_site.resolve` written in plan §4.1 and §5.5. Every hook `artisanpack-ui/cms-framework` actually fires is `ap.`-prefixed with camelCase segments, so the planned name would have been the one hook in the ecosystem matching neither the convention nor the namespace of the package expected to answer it. The listener itself now lives in `artisanpack-ui/core`, so the cms-framework counterpart should be specified against core rather than against this package.
- `.php-cs-fixer.dist.php` sets `blank_line_between_import_groups` explicitly. Without it, the `use` token in `no_extra_blank_lines` strips the blank line between the class and function import groups and the Laravel preset underneath Pint puts it straight back, so `composer fix` and `composer lint` contradicted each other on any file importing both a class and a native function. No file did until `HookSiteResolver` and the provider, which is why the scaffold looked clean. With both rules on, PHP-CS-Fixer collapses stray blank lines within a group and leaves the ones between groups alone — which is what Pint wants too, so the `use` token stays and the standard is not loosened.

### Notes for later work

- The erasure contract is recorded in the migration docblocks and the §9.5 command has to honour all of it. `customer_name` and `customer_email` stay NOT NULL on `bookings` and `booking_series` and are redacted with a placeholder rather than nulled, with `pii_erased_at` set in the same write — a booking has a customer, and that is not a fact the schema should stop asserting to make a later routine's job easier. Two tables hold customer PII without an erasure marker of their own and are easy to miss: `booking_notification_log.recipient` is an address or phone number, reachable by `booking_id` and cascade-deleted with the booking; and `booking_webhook_deliveries.payload` contains the customer's name and email inside stored JSON, which is retention-bound rather than erasure-bound because redacting inside JSON is guesswork. A routine that walks only the four tables carrying `pii_erased_at` leaves the customer's address readable in both.
- `booking_webhook_deliveries` pruning has to actually be scheduled. An unrun prune turns `delivery_retention_days` into a promise nobody keeps, and erasing a booking should delete its payloads immediately rather than waiting out the window.

- Enabling `artisanpack.core.multi_tenant.enabled` on an installation that already holds bookings requires backfilling `site_id` first. Rows written while scoping was off carry a null `site_id`, and the scope matches on equality, so every one of them leaves every site-scoped query the moment a site resolves — `acrossAllSites()` still sees them. Documented in the config block and the README; needs to become a migration-issue checklist item.
- `ap.cmsFramework.currentSite.resolve` still has no producer — `artisanpack-ui/cms-framework` neither fires nor listens to it — so core's `HookSiteResolver` resolves to null in practice today. The counterpart issue belongs on cms-framework, specified against core, and should land before the name is treated as settled.
- `artisanpack-ui/analytics` still ships its own `Traits\BelongsToSite`, `Contracts\SiteResolverInterface`, and `TenantManager` resolver chain. Bookings now resolves through core, so the divergence is one-sided rather than mutual — an application running both still configures tenancy twice until analytics binds against core too.
