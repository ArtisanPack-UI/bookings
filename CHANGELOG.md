# ArtisanPack UI Bookings Changelog

## [Unreleased]

### Added

- The public domain surface from plan §5.1 and §5.4 — the contracts under `src/Contracts/` and eleven new events under `src/Events/`. These are the names `artisanpack-ui/crm` will subscribe to, so they are treated as public API from the moment they land rather than from the moment something uses them.
- `Contracts\SlotResolver`, `RoundRobinStrategy`, `CalendarSyncDriver`, and `NotificationChannel`. Each is a seam an application binds its own implementation into: what counts as a free slot, who gets assigned to it, how one external calendar is talked to, and how one message is delivered. The docblocks carry the rules the callers rely on and cannot enforce — a sync driver's writes have to be idempotent because a timed-out push is indistinguishable from a slow success, and both drivers and channels have to throw on failure because a quiet return leaves a connection looking healthy while it has silently stopped working.
- `Contracts\SiteResolver` was deliberately *not* added. `artisanpack-ui/core` already owns that contract ecosystem-wide, and a second one in this namespace would let an application be site 2 for one package while being site 1 for another — the exact failure core's single-resolver design exists to prevent. Plan §5.1 lists it because it predates core 1.3.
- `Contracts\MeetingType` and `Contracts\MeetingTypeRegistry`, with `MeetingTypes\MeetingTypeRegistry` behind them and bound as a singleton. The four built-in types — `one_to_one`, `group`, `recurring`, `round_robin` — are registry entries rather than arms of a match statement, so an application adding a fifth does the same thing the package does instead of patching around it. Keys are snake_case rather than the plan's `1:1` / `round-robin` prose spellings, because a key is a stored value and every other stored identifier in the package is snake_case. Labels and descriptions are held untranslated and run through `__()` when they are read rather than when the type is constructed — the registry is a singleton, so translating eagerly froze every label at whichever locale happened to be active the first time anything resolved it, which an Octane process or a queue worker serving more than one locale outlives.
- The `ap.bookings.registeredMeetingTypes` filter, per the design-time hook spec. It runs on every read rather than once at boot, so a package registering a type from its own service provider does not have to know whether it boots before or after this one. Filtered entries are re-keyed from each type's own `key()`, so appending with `$types[] =` and assigning to a key behave identically and a type cannot end up registered under a key that disagrees with the one it reports. A subscriber returning a non-array, or an entry that is not a `MeetingType`, throws rather than silently producing an empty or corrupt registry.
- `Events\BookingRequested`, `BookingConfirmed`, `BookingRescheduled`, `BookingCancelled`, `BookingCompleted`, `BookingNoShow`, `SeriesCreated`, `SeriesCancelled`, `SeriesEdited`, `CalendarSynced`, and `CalendarSyncFailed`, joining the existing `CalendarConnectionDisabled` and `WebhookDisabled`.
- `Enums\BookingActor` and `Enums\SeriesEditScope`, both of which exist because the row alone cannot answer the question a listener needs answered. "The customer cancelled" and "we cancelled on the customer" are the same status change and completely different events downstream; a one-off change to a recurring series and a rewrite of the whole arrangement are the same edit and completely different events downstream.
- `Support\TimeRange` and `Support\Slot`, the payload types the contracts are stated in. `TimeRange` is half-open — `[start, end)` — so back-to-back bookings are legal while a genuine double booking is not, and every overlap question in the package is asked of it so the answer cannot differ between two call sites. Endpoints are normalised to `CarbonImmutable`, so a caller that later mutates the Carbon it passed in cannot reach back into a range it already built.
- Event payloads are `readonly`, so the immutability the CRM package will depend on is enforced by the engine rather than by convention — one listener cannot rewrite what the next one sees. This survives the queue: `ReflectionProperty::setValue()` initialises an *uninitialised* readonly property through `zend_update_property_ex()` under the declaring class's scope, which is the same code path on every PHP the package supports, and a promoted property reports `hasDefaultValue() === false`, so `SerializesModels::__serialize()` never skips one and leaves it uninitialised on restore.
- Every event implements `ShouldDispatchAfterCommit`. Plan §5.8 writes bookings inside a transaction and behind an advisory lock, and `SerializesModels` restores a payload by re-reading it from the database — so an event that escaped mid-transaction could reach a queue worker on another connection before the commit landed, and the listener would die with a `ModelNotFoundException` on a booking that does exist. The interface is inert outside a transaction, and it is on the two pre-existing events too, because a dispatch guarantee that holds for eleven of thirteen events is not one anybody can rely on.
- The concrete `MeetingTypes\MeetingTypeRegistry` is aliased to the contract, not just bound behind it. Its constructor takes no arguments, so leaving it unbound let the container quietly auto-build a *second*, empty registry for anyone type-hinting the shipped implementation — losing every PHP-side registration at the call site most likely to be written by somebody reaching for the obvious class.
- `Support\TimeRange::toArray()` normalises to UTC. The endpoints are instants, so the construction zone carries no information the range is entitled to keep — but leaving it in made the serialized text differ between two call sites meaning the identical span, which matters the moment one is stored, sent to an external calendar, or compared as a string. The zone a customer chose lives on the booking, in `customer_timezone`.
- `MeetingTypes\RegisteredMeetingType` falls back to the source string when `__()` hands back something that is not one. `__()` is typed `string|array|null`, a language file may legitimately map a key to an array of lines, and returning that from a method declared `: string` would raise a `TypeError` inside the package for a mistake made outside it.
- `SeriesCancelled` rejects a negative occurrence count. Zero is legitimate — a series whose remaining occurrences had each been cancelled individually — but a negative one reaching a refund listener that multiplies by it moves money the wrong way.
- `SeriesCancelled::$cancelledOccurrenceCount` is required rather than defaulting to zero. The billing and refund listeners the count exists for cannot distinguish a caller who omitted it from a series that had nothing left to cancel, and silently refunding nothing is a worse outcome than a `TypeError` at the call site.
- `CalendarSyncFailed` carries the failure as a message rather than the `Throwable`. Exceptions do not reliably survive the queue — a worker can be handed one whose class is not loadable, or one holding a live database connection — and every event in this set has to.
- Test coverage for the whole surface: every event is dispatched, asserted on, delivered to a registered listener, and round-tripped through `serialize()`/`unserialize()`, since a payload that cannot make that trip fails only in production on a queue worker. Each contract has a plausible application-side implementation under `tests/Fixtures/` proving it is implementable and exercising the rules the docblocks state. The meeting-type filter is covered for adding, replacing, removing, late registration, key disagreement, and both refusal paths.
- The initial migration set — all sixteen tables from plan §4.2, in dependency order: `services`, `service_blackout_dates`, `service_providers`, `service_provider_service`, `availability_schedules`, `availability_overrides`, `booking_series`, `bookings`, `booking_calendar_connections`, `booking_calendar_events`, `booking_calendar_watch_channels`, `booking_webhooks`, `booking_webhook_deliveries`, `booking_notification_log`, `booking_intake_schema_versions`, and `booking_calendar_busy_blocks`. Loaded by the service provider rather than published, so an upgrade that adds a table lands on `migrate` without anybody re-publishing; the `bookings-migrations` tag exists for applications that need to edit the schema.
- The partial unique index guarding a provider's slot — `bookings(provider_id, start_time)` where the status is `requested` or `confirmed`. It is the backstop behind the advisory lock from plan §5.8: if the lock is bypassed, lost, or the write arrives from somewhere that never took it, the second insert fails and the caller retries with the next round-robin candidate. It has to be partial rather than a plain unique, because a plain one would also refuse a customer rebooking a slot they had previously cancelled, which is not a race.
- MySQL has no partial indexes, so the same rule is emulated there with a `VIRTUAL` generated column that evaluates to a slot key while the booking is active and to `NULL` otherwise — MySQL treats `NULL`s as distinct in a unique index, so inactive rows stop competing for the slot for the same reason the `WHERE` clause excludes them on Postgres and SQLite. Unassigned bookings fall out on every engine too: `NULL` columns leave a unique index, and `CONCAT()` with a `NULL` yields `NULL`. An unassigned booking is not holding anybody's slot.
- A second unique index making service and provider slugs unique among rows belonging to no site. `UNIQUE(site_id, slug)` alone says what it means only while a site is resolving: nulls are distinct in a unique index on every supported engine, so on a single-tenant installation — where `site_id` is null on every row, and which is the default configuration — it enforces nothing whatsoever. The plan's "unique per `site_id`" silently excluded the commonest case. Postgres and SQLite index the `site_id IS NULL` predicate directly; MySQL gets the generated-column emulation again. Soft-deleted rows stay in both indexes deliberately, because freeing a trashed slug lets a new row take it and then collide the moment somebody restores the old one — a worse failure than being told up front that the slug is taken.
- `UNIQUE(booking_id, type, scheduled_for)` on `booking_notification_log`, which is what makes the reminder cron idempotent by construction. Sending the 24-hour reminder becomes a claim on a row rather than a decision made by reading, so an overlapping cron, a queue that delivers twice, or a retry after a timeout all race to insert the same key, exactly one wins, and the losers fail cleanly instead of emailing the customer again. `scheduled_for` is null for unscheduled sends, and nulls are distinct in a unique index on all three engines — so two reschedules still produce two emails, which is right.
- Soft deletes and `pii_erased_at` on `services`, `service_providers`, `booking_series`, and `bookings`. The two are not the same thing: a soft delete hides a row while keeping the audit trail, and `pii_erased_at` records that the personal fields on a row that still has to exist were actually cleared.
- Per-engine migration coverage on SQLite, MySQL, and Postgres from one shared definition (`defineBookingMigrationTests()` plus `Tests\Concerns\AssertsBookingSchema`), covering table creation, site-scoping columns, erasure columns, index shape, rollback, and every branch of the slot guard and the notification-log key. Sharing the definitions is the point — the slot guard is two different mechanisms reaching for one rule, so a divergence has to surface as one engine's file failing rather than as a case somebody only ever wrote for SQLite. Each expected-failure insert runs inside its own transaction, because Postgres aborts a transaction on any failed statement and the surrounding test is already in one.
- Package scaffold generated from `package-blueprint`, following `artisanpack-ui/rbac` for the config layout and `artisanpack-ui/pagespeed-insights` for the provider and test conventions.
- `composer.json` — `ArtisanPackUI\Bookings` PSR-4 namespace, `php ^8.2`, `illuminate/support|database|http|notifications ^10.0|^11.0|^12.0|^13.0` (Laravel 13 requires PHP 8.3+ of its own accord, so on PHP 8.2 Composer resolves Laravel 12 or below — the two constraints resolve together rather than conflicting), and required `artisanpack-ui/core`, `artisanpack-ui/hooks`, `artisanpack-ui/security`, `artisanpack-ui/icons`, `nesbot/carbon`, `simshaun/recurr`, and `sabre/vobject` dependencies. `sabre/vobject` is a hard dependency rather than a suggestion because the outbound `.ics` feeds and the CalDAV driver both need RFC 5545 serialization we are not going to hand-roll.
- `suggest` entries for `artisanpack-ui/cms-framework`, `livewire-ui-components`, `forms`, `media-library`, `google`, `microsoft`, `apple`, and `accessibility`. Every one of these is soft: the package has to stay usable in a plain Laravel app, a headless API, or a widget embedded in a site that runs no ArtisanPack CMS at all.
- `Providers\BookingsServiceProvider`, auto-discovered by Laravel, with the `bookings` singleton binding.
- `config/artisanpack/bookings.php` covering timezone, slot interval, availability cache, booking window, cancellation, series, notifications, calendar sync, webhooks, admin and public surfaces, retention, and multi-tenancy. Published under the `bookings-config` tag to `config/artisanpack/bookings.php`, and merged under the matching `artisanpack.bookings` key. Laravel's config loader (`LoadConfiguration::getNestedDirectory`) prefixes keys with the nested directory name, so a published file at that path loads under `artisanpack.bookings`; `mergeConfigFrom` is handed the same key explicitly to match. A bare `bookings` key would have left applications editing a published file the package never reads.
- Every calendar driver ships disabled and `calendar.default_sync_mode` is `outbound`. Two-way sync stays opt-in per connection because it hands an external calendar the power to suppress availability.
- Code style toolchain — `pint.json`, `.php-cs-fixer.dist.php`, and `phpcs.xml`, all three covering `config/` alongside `src/` and `tests/`, with `lint`, `fix`, `cs`, `cs:fix`, and `test` composer scripts. `pint.json` is generated from `artisanpack-ui/code-style-pint`'s `ArtisanPackUIPreset` with five Laravel-preset rules turned off: `phpdoc_no_package` and `no_superfluous_phpdoc_tags` strip the `@package`/`@subpackage`/`@param`/`@return` tags the house PHPDoc standard requires, and `declare_parentheses`, `trim_array_spaces`, and `no_spaces_around_offset` strip the WordPress-style spacing PHP-CS-Fixer's custom fixers add. Left on, Pint and PHP-CS-Fixer would have reformatted each other on alternate runs; `composer fix` now runs Pint first and settles the spacing with PHP-CS-Fixer, and both report clean on the result.
- Pest + Orchestra Testbench setup with a base `TestCase` and coverage of the boot, binding, facade, helper, publish-tag, and config-default paths. The test application registers the core, hooks, and bookings providers and runs against sqlite `:memory:`, and model factories resolve to `ArtisanPackUI\Bookings\Database\Factories\<Model>Factory` — Laravel's default guess looks under `App\Models` and would never find a package factory.
- `Tests\Concerns\TestsWithSqlite`, `TestsWithMysql`, and `TestsWithPostgres`, with matching `mysql` and `postgres` Pest groups and `composer test:sqlite`, `test:mysql`, and `test:postgres` scripts. Booking creation has to be race-safe and the guard is a named advisory lock — MySQL's `GET_LOCK`, Postgres' `pg_advisory_xact_lock` — which sqlite has no equivalent for, so those tests need a real server. They skip when one is unreachable, so `composer test` stays green on a machine with no database running; CI sets `BOOKINGS_REQUIRE_EXTERNAL_DB=1`, which turns the skip into a failure, because a skipped lock test otherwise reads as "race-safety verified" while verifying nothing. `test-mysql` and `test-postgres` jobs run both engines against service containers, and the sqlite matrix excludes the two groups. Harness coverage proves the lock is exclusive across two connections on each engine and that factory names resolve into the package namespace.
- Site resolution comes from `artisanpack-ui/core` (`^1.3`): models scope on whatever `ArtisanPackUI\Core\MultiTenancy\SiteContext` reports, and this package binds no contract, resolver, or configuration block of its own. One place decides which site a request is for, so an application installing several ArtisanPack packages cannot be site 2 for analytics while being site 1 for bookings. Site scoping is switched on in `artisanpack.core.multi_tenant.enabled`, resolvers are listed in `artisanpack.core.multi_tenant.resolvers`, and work that has to target a specific site pins one with `SiteContext::forSite()`.
- `Models\Scopes\BelongsToSiteScope` and the `Models\Concerns\BelongsToSite` trait that opts a model into it — named as a pair after Laravel's own `SoftDeletes`/`SoftDeletingScope`. The scope qualifies `site_id` with the table name so it survives a join, and the trait stamps new records with the site in context unless one was set explicitly. `acrossAllSites()` lifts the scope for maintenance queries such as retention pruning that deliberately span every site. An explicitly set site beats the resolved one, so that deliberate cross-site writes stay possible — which means `site_id` has to stay out of every owning model's `$fillable`, or request data could place a row under another tenant. That rule is documented on the trait and locked in by a test.
- Feature coverage for the multi-tenancy scaffolding: a booking under one site is invisible to a query scoped to another; every row stays visible while site scoping is disabled, when core's shared context is not bound, and when the resolver reports no site; a non-numeric string site identifier scopes and stamps correctly; and a site pinned through `SiteContext::forSite()` scopes queries and stamps writes even while scoping is switched off, which is what a console command looping over sites depends on.

### Changed

- The booking status the specification calls `pending` is `requested`. Plan §5.8 names the slot guard's predicate as `status IN ('requested','confirmed')`, and having the index and the enum disagree about what an unconfirmed booking is called is the kind of thing that is discovered by a race nobody can reproduce. The enum is `requested`, `confirmed`, `cancelled`, `completed`, `no_show`.
- The slot guard also excludes soft-deleted rows, which is one step beyond plan §5.8. A soft-deleted booking is invisible to every domain query, so leaving it in the index would block a slot availability reports as free — and produce a unique violation no retry could resolve, because no candidate provider is the problem. The index has to agree with what the model can see.
- `site_id` is on the seven tables plan §4.3 gives it to, not on all sixteen. The other nine hang off one of those — a busy block belongs to a connection, a schema version to a service, a delivery to a webhook — so they are already reached through a scoped parent. A second copy of the same fact would only add somewhere for it to disagree, and §4.3's per-table schema is the more specific statement of §4.1's rule.
- `availability_overrides` carries an explicit `type` enum (`unavailable` / `custom_hours`) rather than the specification's `is_available` boolean. That boolean had to mean two different things at once — "blocked" and "these hours instead" — and reading a schema should not require knowing which.
- The pivot is `service_provider_service`, per plan §4.2, rather than the specification's `service_provider_services`. Laravel's convention derives a pivot name from the singular models in alphabetical order, so the plan's name is the one the framework will guess without being told.
- `bookings` and `booking_series` restrict deletion of the service and provider they reference rather than cascading or nulling. Both parents are soft deletable, so a hard delete is an explicit destructive act, and letting one silently take every booking ever made against it is the worst outcome available — retention pruning clears the children first and then the parent goes. The `series_id` link is the deliberate exception and still nulls: losing the rule that generated a set of occurrences should not lose the occurrences.
- `services.default_provider_id` and `service_providers.user_id` are indexed but carry no foreign key. `default_provider_id` points at a table created two migrations later and adding the constraint afterwards would need an `ALTER TABLE` SQLite cannot express without rebuilding; `user_id` points at the host application's users table, which a package cannot assume exists or knows the key type of. Same reasoning for `image_media_id` and `oauth_connection_id`, both of which point into suggested packages that may not be installed.
- `security` and `icons` are required at `^2.0`, not the `^1.0` written in plan §3.1. Both packages shipped a 2.x major after the plan was written, and `^1.0` would have pinned bookings to a superseded major — and failed to install alongside the rest of the ecosystem, which is already on 2.x.
- The site-resolution filter is named `ap.cmsFramework.currentSite.resolve`, not the `cms.current_site.resolve` written in plan §4.1 and §5.5. Every hook `artisanpack-ui/cms-framework` actually fires is `ap.`-prefixed with camelCase segments, so the planned name would have been the one hook in the ecosystem matching neither the convention nor the namespace of the package expected to answer it. The listener itself now lives in `artisanpack-ui/core`, so the cms-framework counterpart should be specified against core rather than against this package.
- `.php-cs-fixer.dist.php` sets `blank_line_between_import_groups` explicitly. Without it, the `use` token in `no_extra_blank_lines` strips the blank line between the class and function import groups and the Laravel preset underneath Pint puts it straight back, so `composer fix` and `composer lint` contradicted each other on any file importing both a class and a native function. No file did until `HookSiteResolver` and the provider, which is why the scaffold looked clean. With both rules on, PHP-CS-Fixer collapses stray blank lines within a group and leaves the ones between groups alone — which is what Pint wants too, so the `use` token stays and the standard is not loosened.

### Notes for later work

- The erasure contract is recorded in the migration docblocks and the §9.5 command has to honour all of it. `customer_name` and `customer_email` stay NOT NULL on `bookings` and `booking_series` and are redacted with a placeholder rather than nulled, with `pii_erased_at` set in the same write — a booking has a customer, and that is not a fact the schema should stop asserting to make a later routine's job easier. Two tables hold customer PII without an erasure marker of their own and are easy to miss: `booking_notification_log.recipient` is an address or phone number, reachable by `booking_id` and cascade-deleted with the booking; and `booking_webhook_deliveries.payload` contains the customer's name and email inside stored JSON, which is retention-bound rather than erasure-bound because redacting inside JSON is guesswork. A routine that walks only the four tables carrying `pii_erased_at` leaves the customer's address readable in both.
- `booking_webhook_deliveries` pruning has to actually be scheduled. An unrun prune turns `delivery_retention_days` into a promise nobody keeps, and erasing a booking should delete its payloads immediately rather than waiting out the window.

- Enabling `artisanpack.core.multi_tenant.enabled` on an installation that already holds bookings requires backfilling `site_id` first. Rows written while scoping was off carry a null `site_id`, and the scope matches on equality, so every one of them leaves every site-scoped query the moment a site resolves — `acrossAllSites()` still sees them. Documented in the config block and the README; needs to become a migration-issue checklist item.
- `ap.cmsFramework.currentSite.resolve` still has no producer — `artisanpack-ui/cms-framework` neither fires nor listens to it — so core's `HookSiteResolver` resolves to null in practice today. The counterpart issue belongs on cms-framework, specified against core, and should land before the name is treated as settled.
- `artisanpack-ui/analytics` still ships its own `Traits\BelongsToSite`, `Contracts\SiteResolverInterface`, and `TenantManager` resolver chain. Bookings now resolves through core, so the divergence is one-sided rather than mutual — an application running both still configures tenancy twice until analytics binds against core too.
