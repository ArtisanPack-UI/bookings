### 1.2 Booking cancellation never propagates to connected calendars (HIGH)

- **Files:** `src/Listeners/SyncBookingToCalendar.php:53-57` (docblock says removal-on-cancel "is tracked separately" — nothing implements it), `src/Services/CalendarSyncOrchestrator.php` (no cancel path).
- **Failure:** customer cancels a confirmed booking → the Google Calendar event stays `confirmed` on the provider's calendar forever. A test even enshrines that cancellation does *not* sync.
- **Fix:** add a `BookingCancelled` handler to `SyncBookingToCalendar` that, per `CalendarEvent` ledger row for the booking, dispatches `RemoveBookingFromCalendars` (the job exists at `src/Jobs/RemoveBookingFromCalendars.php` and the ledger already knows every calendar the booking is on). Alternative minimal fix: re-push on cancel — `GoogleCalendarDriver::buildEvent()` already maps `BookingStatus::Cancelled → 'cancelled'`.
- **Tests:** update the listener test that currently asserts cancellation does nothing; add a test that `BookingCancelled` dispatches the removal (or status-flip push) per connection.

### 1.3 Calendar refresh / watch-renew sweeps are inert no-ops (HIGH)

- **Files:** `src/Console/Commands/RefreshCalendarsCommand.php:79-93`, `src/Console/Commands/RenewCalendarWatchChannelsCommand.php:85-99`, `src/Console/Commands/Concerns/SweepsCalendarConnections.php:55-63`.
- **Problem:** both commands only `count()` the due rows and then unconditionally print "No calendar sync driver is installed, so nothing was synced" — they never consult `CalendarDriverRegistry` and nothing in the package ever calls `incrementalSync()`, `busyPeriods()`, `subscribeToChanges()`, or `renewSubscription()` (grep-verified: zero call sites outside the drivers/contract). With `artisanpack-ui/google` installed, watch channels expire after ~7 days and are never renewed; busy blocks silently go stale; customers book over real events. The warning text is also wrong when a driver *is* registered.
- **Fix:** in both commands, resolve the due connection's driver from `CalendarDriverRegistry`; when present, invoke it (`renewSubscription()` for the watch command; `incrementalSync()`/`busyPeriods()` ingestion for the refresh command, mirroring how `CalendarSyncOrchestrator` records failures); only print the "not installed" warning when the driver is genuinely absent. If the two-way wiring is intentionally deferred to the companion packages, replace the body with a hook the driver package subscribes to and correct the docs — but decide on record; as shipped the Google driver's entire two-way surface is dead code.
- **Tests:** extend `tests/Feature/Console/CalendarSweepCommandsTest.php` with a fake registered driver asserting it gets invoked for due connections.

### 1.4 Forms integration bypasses the booking window (MEDIUM, ships a real bypass)

- **Files:** `src/Integrations/Forms/BookingSlotField.php:293-309`, `src/Services/BookingService.php:295-351` (`formSubmissionIsBookable`) and `:229-259` (`createFromFormSubmission`); reference implementation at `src/Http/Requests/Public/StoreBookingRequest.php:279-296` (`validateBookingWindow`).
- **Failure:** the forms path re-checks slot *availability* but never `BookingWindow::earliest()/latest()`; availability deliberately knows nothing about "now", so a tampered or stale form payload books a past slot or one inside the minimum-notice window — a slot the widget and HTTP API would refuse.
- **Fix:** in `formSubmissionIsBookable()` (and/or `createFromFormSubmission()`), reject `$start` before `BookingWindow::earliest( now )` or after `BookingWindow::latest( now )` — the same clip `StoreBookingRequest` applies.
- **Tests:** new cases: a form submission naming a past slot, and one inside `min_advance_minutes`, are both refused.

### 1.5 `BookingWindow::day()`/`month()` end bound drifts across DST (MEDIUM)

- **File:** `src/Support/BookingWindow.php:68` (`$start->utc()->addMonth()`) and `:95` (`$start->utc()->addDay()`).
- **Failure (Carbon-verified):** the span end adds a day/month to the **UTC instant**, so `day( $service, '2026-11-01', 'America/Chicago' )` ends at `2026-11-02 05:00Z` instead of the true next local midnight `06:00Z` — the 23:00–24:00 local slots vanish from the fall-back day, and `ManageBooking::withinBookingWindow()` (`src/Livewire/Public/ManageBooking.php:945-948`) refuses a legitimate reschedule. Spring-forward leaks the next day's 00:00–01:00 slots in. Note `AvailabilityService::computeDay()` does this correctly — only `BookingWindow` is wrong.
- **Fix:** add the period in the local zone before converting: `self::clip( $start->utc(), $start->addDay()->utc() )` (and `addMonth()` likewise).
- **Tests:** add DST cases to `tests/Feature/Support/BookingWindowTest.php` — `2026-11-01` and `2026-03-08` in `America/Chicago` for `day()`, November 2026 for `month()`.

## Phase 2 — Security hardening (all LOW; none block release, do 2.1–2.2 if time allows)

No critical or high security findings anywhere. Verified solid: SSRF guard enforced at save *and* delivery with address pinning and redirect refusal; HMAC-signed webhooks with `hash_equals`; CSPRNG manage/iCal tokens stored hashed, shape-checked, uniform-404, doubly rate-limited; site scoping via global scope with `#[Locked]` ids throughout the admin; fail-closed admin gate registered as Livewire persistent middleware (`BookingsServiceProvider.php:567` — load-bearing, don't remove); field-by-field mass-assignment rebuilds; sabre/vobject ICS with sanitized filenames; sanitization-before-validation with depth-budgeted intake payloads; JS widgets free of DOM-XSS sinks, `postMessage`, storage, and credentials; public views/emails free of raw echoes and script interpolation.

1. **Rate-limit the public GET endpoints.** `routes/public.php:40-47` — `GET services`, `GET services/{slug}/providers`, `GET services/{slug}/slots` have no package throttle, and slot resolution is the most expensive read in the package. Add a `read` bucket to `RateLimitBookings::DEFAULTS` (`src/Http/Middleware/RateLimitBookings.php`) + `config/artisanpack/bookings.php` `public.rate_limits`, attach `bookings.rate-limit:read` to the three routes, document in `docs/advanced/rate-limiting.md`.
2. **Encrypt webhook signing secrets.** `src/Models/Webhook.php:99-105` — add `'secret' => 'encrypted'` to the casts (currently plaintext in `booking_webhooks`; a DB dump lets an attacker forge signed deliveries). Add a release note re: existing rows.
3. **Per-token bucket on manage POSTs.** `routes/public.php:78-84` — add `bookings.rate-limit:manage_token` before `bookings.manage-token` on the cancel/reschedule POSTs, matching the GET's stack.
4. **Warn when address pinning can't apply.** `src/Services/WebhookDispatcher.php:447-451` — `CURLOPT_RESOLVE` pinning silently degrades on non-curl transports/old libcurl. Log a warning (or refuse) when `! defined( 'CURLOPT_RESOLVE' )` or the curl handler isn't in use.
5. **Validate `imageMediaId` against the media library.** `src/Livewire/Admin/ProviderEditor.php:425` accepts any positive integer. When `class_exists( Media::class )`, add a closure rule resolving through the media library's scoped query (mirror `ServiceEditor.php:381`'s pattern).
6. **Design note (document, don't change):** admin authorization is a single `bookings.admin` gate — anyone holding it can erase PII, delete providers, manage webhooks. Fine for v1.0's single-role model; document it, and consider per-surface gates (`bookings.erase-pii`, …) defaulting to the main gate in a minor release.
7. **Doc tweak:** `resources/js/core/api-client.ts:56-59` — the `headers` option doc says "e.g. … a custom token"; reword to warn any header value ships in public page source.

## Phase 3 — Correctness fixes that can ride in 1.0.1

1. **Google 409 on tombstoned event ids treated as success.** `src/Drivers/Calendar/GoogleCalendarDriver.php:188-194` and re-insert path `:222-228`. Reassign A→B→A: insert with the retained id returns 409 while the event stays `cancelled`; the driver records success and the appointment never renders. **Fix:** on 409, follow with a PUT to the same id (resurrects the event with current body/status). Add a test for the reassign-back scenario.
2. **Webhook retry chain not crash-safe.** `src/Jobs/DispatchWebhookDelivery.php:97-122` (`$tries = 1`, retry re-queued by the failing attempt), `src/Services/WebhookDispatcher.php:220-231`. A worker crash between writing the `failed` row and re-dispatching strands the delivery forever; `WebhookDelivery::scopeDue()` was written for a sweep that doesn't exist. **Fix:** ship the retry sweep command using `scopeDue()` with the compare-and-set claim the docblock prescribes; schedule it alongside the other sweeps in the provider.
3. **Series split miscounts after a customer reschedule.** `src/Services/SeriesService.php:644-712` (`splitSeries`), `:875-886` (`countBefore`); `ManageBooking.php:500` reschedules without detaching. Count by the anchor's `series_index` instead of comparing wall instants (or detach occurrences rescheduled off their rule instant). Test: reschedule occurrence #5 of a COUNT=12 weekly series, then split "this and following" — tail must get COUNT=7.
4. **Spring-forward boundary inside the DST gap 500s the whole day.** `src/Models/AvailabilitySchedule.php:310-318`, `src/Models/AvailabilityOverride.php:261-269` throw for a nonexistent local time; `AvailabilityService::availabilityWindows()` (`:453-474`) never catches. A valid `02:30` row breaks that provider's entire day once a year, on the public path. **Fix:** clamp the boundary to the post-transition instant (or skip the window) in `availabilityWindows()`; keep the throw for genuinely unparseable values.
5. **Zero-duration service produces a misleading hook-contract exception.** `src/Services/AvailabilityService.php:767-786`: `duration = 0` throws "ap.bookings.slotDuration must return a positive integer". Clamp/validate before the filter runs (and/or forbid 0 at write time in `ServiceEditor` validation).
6. **Reminder catch-up has no staleness floor.** `src/Services/ReminderScheduler.php:158-163, 204-213` — after cron downtime a "24-hour" reminder can fire minutes before start. Optional config cutoff (skip moments more than N hours past).
7. **Migration `2026_08_18_…_add_provider_types_to_booking_notification_log.php` `down()`** narrows the enum without first deleting rows holding the new values (MySQL coerces/errors, Postgres constraint fails). Delete `WHERE type IN ('provider_assigned','provider_unassigned')` rows inside `down()` first.
8. **Release-note items (no code change required):** notifications render in app locale, not per-customer (`BookingNotification` sets no `locale()`); webhook payloads include `intake_data` + customer PII to every subscribed endpoint (`src/Listeners/DispatchBookingWebhooks.php:243-281`) — consider a payload filter hook or config flag later.
